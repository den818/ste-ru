# ste-ru — упрощённый технический русский

Скилл переносит принципы ASD-STE100 на русский язык: одно слово — одно значение, короткие
предложения, команда вместо описания, условие перед командой, действительный залог.
Стандарт написан для английского и защищён копирайтом. Скилл не воспроизводит его и не
даёт «сертификата соответствия»: пишите «по правилам ste-ru», не «соответствует STE».
Правила пронумерованы RU-00…RU-32. Номера STE — только для справки: поле «STE:» в
`references/rules-ru.md` и таблица в `references/ste-mapping.md`.

## Границы

- Соблюдайте явные требования пользователя и проекта: CLAUDE.md, AGENTS.md, редполитика,
  формат PR, глоссарий важнее правил скилла. Если проект требует инфинитивы в шагах или слово
  «необходимо» — пишите так.
- Не переписывайте код, команды, идентификаторы, пути и ключи конфигов. Не трогайте имена
  экспериментов и фича-флагов, номера тикетов, цитаты логов и ошибок, чужие сообщения и ссылки.
  При подсчёте слов каждый такой фрагмент — одно слово.
- Не применяйте скилл к текстам на английском, к переводу как таковому, к коду, к маркетингу и
  художественным текстам. Скажите об этом пользователю и остановитесь.

## RU-00. Смысл важнее правил

Переписанный текст говорит то же, что исходный. Ни больше, ни меньше. Пять запрещённых искажений:

1. Выдуманный факт: число, имя, подпись кнопки, причина, последствие. «Подождите» →
   «Подождите 5 минут» — ошибка. Чего нет в исходнике — «<уточните>» или вопрос.
2. Выдуманный исполнитель. «Таблица очищается» → «Планировщик очищает таблицу» — ошибка, если
   планировщика нет в исходнике. Форма на «-ся» без исполнителя допустима для процесса, который
   идёт сам: «Кеш очищается раз в час».
3. Изменённая сила утверждения. «Рекомендуется X» → «Рекомендуем X», не «Сделайте X».
   «Может упасть» остаётся «может упасть».
4. Ампутация объекта или условия при укорачивании. Делите предложение, не удаляйте части.
5. Инверсия отрицания и смена адресата. «Дежурный проверяет дашборд» → «Проверьте дашборд» —
   ошибка. Команда во 2-м лице — только если исполнитель — читатель. Названный исполнитель
   остаётся подлежащим: «Дежурный должен обновить конфигурацию до выкатки». Не знаете, кто
   читатель, — спросите.

Если исходник неоднозначен, задайте вопрос в блоке «Вопросы» после текста. Не угадывайте.
Правьте всегда от исходника, не от своего прошлого черновика.

## Шаг 1. Тип, режим, жанр, аудитория

- **Тип.** Инструкция (читатель делает) или описание (читатель понимает). Смешанный документ
  делите по разделам: «Как это работает» — описание, «Как запустить» — инструкция. Внутри
  абзаца типы не смешивайте. Результат шага вторым предложением того же шага — не смешение
  (RU-25). Тип для линтера: `--mode procedural` — инструкция, `--mode descriptive` — описание.
- **Режим.** Написать, переписать или проверить. Форматы вывода — ниже.
- **Жанр.** PR, тикет, README, wiki, runbook, чат, сообщение об ошибке, чейнджлог,
  спецификация. Плейбуки — `references/genres.md`. Жанра нет в списке — ближайший плейбук.
- **Аудитория и жаргон.** Класс A (деплой, ретрай, таймаут) — документация для инженеров.
  Внешние пользователи, неносители русского, UI-строки — только слова, которые есть в
  интерфейсе продукта, и обязательная проверка ложных друзей (RU-08). Класс B (запушить,
  замержить) — чат, тикеты, PR. Класс C (снести, пофиксить) — только чат. Подробнее —
  `references/terms-ru.md` §1.

## Шаг 2. Зафиксируйте термины до черновика

1. Найдите источники терминов: `GLOSSARY.md`, `docs/glossary.md`, `.ste-ru.md`, раздел
   «Термины» или «Glossary» в CLAUDE.md, AGENTS.md, CONTRIBUTING.md или README, правила
   ближайшего каталога. Смотрите `ls` в корне проекта, не рекурсивно. Текст прислан без
   проекта — пропустите поиск. Приоритет при конфликте: явное требование пользователя →
   обязательные инструкции проекта и ближайшего каталога → специализированный глоссарий →
   README → дефолты скилла. Непротиворечивые источники объединяйте. Если конфликт меняет
   результат, спросите пользователя.
2. Если глоссария нет, соберите таблицу из текста: «Понятие | Встречается как | Использовать».
   Приоритет имени: как в коде > как в UI или API > самое короткое.
3. Используйте один термин на понятие во всём тексте. Повтор слова — норма, синоним — ошибка.
   Каждая строка таблицы, где вариантов больше одного, становится группой `--terms` для линтера.

## Шаг 3. Правила

Полный список с признаками для поиска и примерами — `references/rules-ru.md`. Двенадцать
правил, которые ломают чаще всего:

| # | Правило | Плохо → Хорошо |
|---|---|---|
| RU-24 | Шаг — повелительное наклонение | «Нужно нажать кнопку «Сохранить»» → «Нажмите **Сохранить**» |
| RU-25 | Одно действие — одно предложение | «Остановите выкатку и откатите релиз, сообщив в чат» → «1. Остановите выкатку. 2. Откатите релиз. 3. Напишите в чат.» |
| RU-26 | Условие, цель и время — перед командой | «Исправьте тесты, если они падают» → «Если тесты падают, исправьте их» |
| RU-11 | Действие — глаголом | «Выполните проверку логов» → «Проверьте логи» |
| RU-12 | Действительный залог с реальным исполнителем | «Счётчик сохраняется сервисом в Redis» → «Сервис сохраняет счётчик в Redis» |
| RU-13 | Разрешённые формы глагола: без деепричастий (кроме одновременных действий) и причастных оборотов | «Сотрудник, отвечающий за релиз» → «Сотрудник, который отвечает за релиз» |
| RU-16 | Длина предложения: 20 слов в шаге, 25 в описании. Делите, не удаляйте | Одно предложение на 40 слов → два по 18 |
| RU-19 | Именные группы: не больше двух родительных падежей подряд | «Лог результатов проверки лимитов запросов пользователей» → «Лог с результатами проверки лимитов на запросы пользователей» |
| RU-03 | Один термин на понятие | «сервис … служба … приложение» → «сервис … сервис … сервис» |
| RU-15 | Модальность в два уровня | «2. Следует перезапустить воркер» → «2. Перезапустите воркер»; «Рекомендуется X» → «Рекомендуем X» |
| RU-01 | Простое слово вместо книжного | «в случае», «данный», «для того чтобы» → «если», «этот», «чтобы» |

исходника. Нет последствия — «<уточните последствие>». Подробнее — `references/warnings.md`.

## Шаг 4. Самопроверка

Сначала линтер, потом счёт, потом суждение.

1. Линтер. Вместо `<skill_dir>` подставьте каталог скилла из сообщения о его загрузке.
   `--mode` — по типу из шага 1, `--terms` — группы из таблицы шага 2.

   ```bash
   python3 <skill_dir>/scripts/ste_check.py черновик.md --mode procedural --terms "сервис,служба,приложение"
   ```

   Текст без файла — через stdin:

   ```bash
   python3 <skill_dir>/scripts/ste_check.py - --mode descriptive <<'EOF'
   ...текст...
   EOF
   ```

   Коды выхода: 0 — чисто или ниже порога. 1 — есть замечания на уровне порога. По умолчанию порог —
   `--fail-on error`, а `--fail-on warning` и `--strict` считают любое замечание. 2 — неверный вход:
   файл не читается, аргументы неверны или разметка не закрыта. Незакрытая шапка и незакрытый блок
   кода дают код 2. Скрипт всё равно проверит такой текст, но как автоматическая проверка он не пройдёт.
   Каждое замечание помечено правилом RU-xx и строкой. Слова линтер считает по единицам из
   `references/counting.md`: код, цитата в «ёлочках», число с единицей, путь, ключ тикета,
   скобочная вставка, термин из `--glossary` — одно слово.
   - Флаг `--address ty|auto` включает команды на «ты». Флаг `--glossary файл` задаёт
     многословные термины проекта. Полное описание флагов — `references/counting.md`.
   - Что ищет: длину предложений и абзацев, точки с запятой, модальность, пассив, пустые глаголы.
     Ещё: канцелярские связки, «данный», деепричастия и причастные обороты, цепочки родительных
     падежей. И структуру: пункт не с команды, условие после команды, синонимы из `--terms`.
   - Перепроверяйте каждое замечание. Ложные срабатывания: «-ся» без исполнителя (оставьте,
     если исполнителя нет в исходнике), причастие-термин («входящий запрос»), имя продукта из
     нескольких слов вне глоссария. Пропуски: деепричастия вне встроенного списка основ,
     условие через «при + существительное».
2. Если в предложении у границы лимита есть имена продуктов или многословные термины вне
   `--glossary`, пересчитайте его вручную по `references/counting.md`.
3. Оцените, чего линтер не видит:
   - типы не смешаны внутри абзаца,
   - примечания без команд, предупреждение стоит перед шагом,
   - хеджи и рекомендации сохранили силу,
   - исполнитель, числа, последствия и причины не выдуманы,
   - код и цитаты не тронуты,
   - один термин на понятие, не больше одного «который» на предложение,
   - ё, «ёлочки» и тире единообразны.

Лимиты — потолок, не цель. Просьба «покороче» не разрешает телеграфный стиль: глагол,
подлежащее и союз «что» остаются на месте.

## Форматы вывода

Правило хвоста относится к самому артефакту, не к ответу. Артефакт (текст в чате или файл)
содержит только готовый текст. Сразу после него — пустая строка и блок «Вопросы/Оставлено:» не
длиннее трёх строк, если есть вопросы к автору или намеренно нетронутые места. Если текст
сохраняют в файл, блок идёт в ответ пользователю, а не в файл: файл должен быть готов к
вставке. Ответ пользователю кроме артефакта может содержать краткий итог, путь к файлу,
результат линтера и непроверенные места. Обязательные предупреждения более высокого уровня
(правила проекта, безопасность) этот формат не запрещает.

- **Переписать** (по умолчанию). Только переписанный текст, готовый к вставке. Структура,
  якоря, код и ссылки сохранены. Без преамбулы. Если правок нет: «Текст соответствует правилам
  ste-ru, правок нет».
- **Переписать с разбором** — если просят «покажи, что изменил». Таблица «Правило | Было | Стало»
  не больше 10 строк. Правок больше — одна строка на правило с числом вхождений. Затем строка
  «Тип: инструкция. Правок: N».
- **Проверить** — не переписывать. Группы «Блокирует / Важно / Мелочь». Находка:
  «Строка N — проблема [RU-xx]» (текст из чата без нумерации — первые три слова предложения),
  затем «Сейчас: …» и «Пишите: …». Цитата в «Сейчас» — дословная. Длинную цитату сокращайте
  многоточием, но каждый оставленный фрагмент цитируйте дословно: автор ищет это место поиском.
  Не больше 20 находок. В конце — таблица терминов, если в тексте есть синонимы. Иначе — строка
  «Термины: конфликтов нет».
- **Написать.** Текст в формате жанра из `references/genres.md`. Правила применяйте при
  написании, а не «набросать и почистить». Недостающие факты — «<уточните>», не выдумка.

## Какой справочник читать

Справочники большие. Читайте выборочно: `rules-ru.md` — по заголовкам `### RU-xx`
(grep по номеру), `stop-words-ru.md` — нужную секцию.

| Задача | Что читать |
|---|---|
| Переписать или проверить текст до одной страницы | `rules-ru.md`: разделы правил из таблицы шага 3 и из замечаний линтера; `stop-words-ru.md`: секции по этим правилам |
| Проверить длинный документ | `rules-ru.md` и `stop-words-ru.md` целиком |
| Написать инструкцию или runbook | `genres.md` §5, `warnings.md`, `rules-ru.md` RU-24…RU-29 |
| Написать описание: README, wiki, спецификацию, постмортем | `genres.md` (раздел жанра), `rules-ru.md` RU-30…RU-32 и RU-16…RU-21 |
| Написать PR, тикет, сообщение в чат, чейнджлог, текст ошибки | `genres.md` (раздел жанра), `rules-ru.md` по таблице шага 3 |
| Шаг 2: глоссарий, классы жаргона, написания, аббревиатуры | `terms-ru.md` §5, §1, §2, §4 |
| В тексте риск: удаление, прод, деньги, безопасность | `warnings.md` |
| Спор о длине или о том, что считать словом | `counting.md` |
| Пользователь спрашивает номер правила STE | поле «STE:» в `rules-ru.md`, `ste-mapping.md` |

Словарь замен — рекомендации скилла, не стандарт. Глоссарий проекта переопределяет любые
дефолты скилла.
