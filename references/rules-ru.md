# Правила ste-ru

Этот файл — канонический список правил скилла ste-ru: RU-00…RU-32 в шести блоках.
Номер правила — «RU-» и две цифры. Блок 0 — смысл, A — слова, B — глаголы, C — предложения, D — инструкции, E — описания и оформление.
Поле «STE:» — номера правил ASD-STE100 Issue 9, на которые опирается правило. Это ссылки, не цитаты: текст стандарта здесь не воспроизводится. Правила с пометкой «RU-only» — эвристики ste-ru: их опора — справочник Розенталя, русские редполитики и практика скилла. Часть правил совпадает с ГОСТ Р 58049-2017 (упрощённый технический русский), раздел 8.2 — сверено по первоисточнику, таблица соответствия и расхождения в `ste-mapping.md`. Стандарт написан для эксплуатационной документации авиационной техники, поэтому для читателя он аргумент, а не обязательная норма: называйте правила правилами ste-ru. После сверки здесь появятся издание, дата и точные границы подтверждённых утверждений.
Глоссарий проекта переопределяет дефолты этого файла: термины, написание, классы жаргона, белый список аббревиатур.
Примеры помечены как [жанр; режим]. Каждый пример «Хорошо» сохраняет все факты примера «Плохо».

## 0. Смысл

### RU-00. Смысл важнее правил
**STE:** 9.1, 3.6
**Правило.** Сохраняйте смысл исходника: факты, силу утверждений, исполнителя, адресата. Делите длинное предложение, а не удаляйте его части. Код, команды, идентификаторы, цитаты логов и чужие сообщения не трогайте. Правило RU-00 имеет приоритет над любым другим правилом этого файла.
**Почему.** Правка ради правила ломает текст незаметно: читатель получает короткий, убедительный и ложный текст. Переводчик и агент переносят искажение дальше.
**Ищите.** Пять искажений при переписывании:
- Выдуманный факт: «Перезапустите сервис» → «Перезапустите сервис через 5 минут». Числа в исходнике не было.
- Выдуманный исполнитель: «Запись удаляется через 30 дней» → «Планировщик удаляет запись через 30 дней». Кто удаляет — неизвестно.
- Изменённый хедж: «Возможно, проблема в кеше» → «Проблема в кеше». Догадка стала фактом. Обратное тоже искажение: «Сделайте бэкап» → «Рекомендуем сделать бэкап».
- Ампутация объекта или условия: «Если тесты прошли, выкатите релиз» → «Выкатите релиз». Условие потеряно.
- Инверсия отрицания: «Не все запросы проходят» → «Запросы не проходят». Смена адресата: «Дежурный проверяет дашборд» → «Проверьте дашборд».
Три приёма защищают смысл. Делите, не удаляйте: длинное предложение → два коротких с теми же словами. Если исходник неоднозначен, задайте вопрос одной строкой или поставьте «<уточните>». Каждую новую версию делайте из оригинала, а не из предыдущего черновика, иначе искажения копятся.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Если после деплоя в логах есть ошибки `connection refused`, откатите релиз и напишите в чат дежурных, потому что база, скорее всего, не успела запуститься.» → Хорошо: «Если после деплоя в логах есть ошибки `connection refused`, откатите релиз. Напишите в чат дежурных. Причина, скорее всего, в том, что база не успела запуститься.» — условие, оба действия, причина и хедж «скорее всего» сохранены. Предложение только разделено, порядок действий не добавлен.
- [wiki; переписывание] Плохо: «Перед выкаткой стоит прогнать нагрузочные тесты, если есть время.» → Хорошо: «Если есть время, рекомендуем прогнать нагрузочные тесты перед выкаткой.» — «стоит» → «рекомендуем»: рекомендация осталась рекомендацией. Варианты «Прогоните тесты» и «можно прогнать» изменили бы силу утверждения.
- [инструкция; переписывание] Плохо: «Выставьте нужный таймаут в конфиге.» → Хорошо: «Задайте в конфиге таймаут <уточните: значение>.» — значения в исходнике нет. Плейсхолдер и вопрос автору вместо выдуманного числа.
**Исключения.** В режиме написания автор сам решает, что утверждать. Явное требование пользователя («сделай жёстче», «убери оговорки») меняет силу утверждений. Без такого требования — нет.

## A. Слова

### RU-01. Простое слово вместо книжного
**STE:** 1.1, 1.6, 9.1
**Правило.** Выбирайте самое частотное слово с тем же смыслом. Книжные и канцелярские слова замените простыми: «задействовать» → «использовать», «функционировать» → «работать», «посредством» → «через» или творительный падеж, «данный» → «этот». Заимствование без нужды («аллоцировать», «нотифицировать») → русский глагол («выделить», «сообщить»). Полный словарь замен — `stop-words-ru.md`. Пустые глаголы и расщеплённые сказуемые («осуществить перезапуск») — RU-11.
**Почему.** Редкое слово читают медленнее и переводят хуже. У простого слова одно значение, и оно не требует словаря. Агент копирует книжный стиль в следующие тексты.
**Ищите.**
- Глаголы на «-ировать» с русской парой: аллоцировать, нотифицировать, инициировать, детектировать.
- Предлоги-связки: посредством, в рамках, в целях, касательно, на предмет, в ходе.
- Заместители: данный, указанный, соответствующий, вышеупомянутый.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Запустите данный воркер посредством команды `systemctl start worker`.» → Хорошо: «Запустите этот воркер командой `systemctl start worker`.» — «данный» → «этот», «посредством» → творительный падеж.
- [wiki; написание] Плохо: «Данный сервис функционирует в режиме активного ожидания и аллоцирует память при старте.» → Хорошо: «Этот сервис работает в режиме активного ожидания и выделяет память при старте.» — три книжных слова заменены частотными. Термин «режим активного ожидания» сохранён.
- [PR; переписывание] Плохо: «В рамках данного PR реализована возможность отключения ретраев.» → Хорошо: «Этот PR добавляет возможность отключить ретраи.» — «в рамках», «данный», «реализована» ушли. Факт тот же.
**Исключения.** Термин остаётся, даже если он книжный: «инициализация», «аллокация», «валидация» как имена понятий из кода или глоссария.

### RU-02. Одно слово — одно значение
**STE:** 1.3, 9.2, 9.3
**Правило.** Каждое слово — в одном прямом значении на весь текст. Бытовые глаголы в переносном значении замените глаголом, который называет действие прямо: «поднять» → «запустить», «завести» → «создать», «прокинуть» → «передать». Полный список — `stop-words-ru.md` §9. Если у слова в проекте два значения («ключ» — шифрования, API, словаря, флаг команды), разведите их разными словами.
**Почему.** Читатель вне команды и переводчик понимают метафору буквально или гадают. Одно слово в двух значениях в одном тексте читатель принимает за две сущности.
**Ищите.**
- Глаголы движения и положения о сервисах: поднять, лечь, упасть, висеть, лежать, стоять, крутиться, ходить.
- Переносные бытовые глаголы: снять, завести, повесить, прокинуть, подтянуть, разгрести, отвалиться.
- Слова с двумя значениями рядом: ключ, запись, клиент, сессия, поле.
**Плохо → Хорошо.**
- [тикет; переписывание] Плохо: «После миграции сервис лёг с ошибкой `out of memory`, а очередь встала.» → Хорошо: «После миграции сервис завершился с ошибкой `out of memory`. Очередь остановилась.» — два переносных глагола названы прямо. Цитата ошибки задаёт значение «лёг»: процесс завершился, а не перестал отвечать. «Встала» → «остановилась»: буквальный глагол без догадки о причине.
- [README; написание] Плохо: «Ключ хранится в Vault, а ключ `user_id` передаётся в теле запроса.» → Хорошо: «Ключ шифрования хранится в Vault, а поле `user_id` передаётся в теле запроса.» — «ключ» в двух значениях. Для элемента тела запроса есть слово «поле».
- [README; переписывание] Плохо: «Клиент отправляет токен в заголовке. Если токен истёк, клиент увидит ошибку на экране.» → Хорошо: «Клиент отправляет токен в заголовке. Если токен истёк, пользователь увидит ошибку на экране.» — «клиент» в двух значениях: программа и человек. Для человека есть слово «пользователь» (см. `terms-ru.md` §6).
**Исключения.** Метафора, которую глоссарий закрепил как термин, допустима в одном значении: «выкатить» — выпустить релиз в окружение, «упасть» — завершиться аварийно. Тогда остальные значения этого слова запрещены. В чате переносный глагол допустим, если его смысл однозначен.

### RU-03. Один термин на понятие
**STE:** 1.5, 1.8, 1.11, 9.4, 6.2
**Правило.** Называйте объект так, как он назван в коде, конфиге, UI или глоссарии проекта. Один термин на понятие на весь текст: не заменяйте его синонимом, аббревиатурой, переводом или описанием. Повтор термина — норма. Порядок поиска глоссария и приоритет имён (код > UI/API > самое короткое) — в `terms-ru.md`.
**Почему.** Синонимы читатель принимает за разные сущности и ищет разницу, которой нет. Описание вместо имени заставляет гадать. Перевод имени создаёт второе имя, которое не найти поиском.
**Ищите.**
- Пары в одном тексте: сервис/приложение/система, конфиг/настройки/параметры, ошибка/сбой/проблема, пользователь/юзер/клиент.
- Пары для одного действия: нажмите/кликните/щёлкните, удалите/уберите/снесите, ручка/эндпоинт/метод.
- Описания там, где есть имя: «файл с настройками», «главная ветка», «таблица с заказами».
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Откройте PR в главную ветку. После мержа в main запустится сборка.» → Хорошо: «Откройте PR в main. После мержа в main запустится сборка.» — «главная ветка» и main — один объект под двумя именами. Имя из репозитория побеждает.
- [инструкция; написание] Плохо: «Проверьте таблицу с заказами в базе.» → Хорошо: «Проверьте таблицу `orders` в базе `orders_db`.» — у таблицы и базы есть имена в схеме. Автор в режиме написания их знает.
- [README; переписывание] Плохо: «Ручка `/v1/orders` возвращает список. Эндпоинт `/v1/orders/{id}` возвращает один заказ.» → Хорошо: «Эндпоинт `/v1/orders` возвращает список. Эндпоинт `/v1/orders/{id}` возвращает один заказ.» — два имени одного понятия сведены к одному. «Ручка» допустима в чате и тикетах, «эндпоинт» — везде.
**Исключения.** Разные слова для разных понятий: «ошибка» (error) и «сбой» (failure), «инцидент» (outage), «клиент» (программа) и «пользователь» (человек). Первое упоминание термина с пояснением в скобках: «секретница (хранилище секретов)» — дальше только термин. Без глоссария — таблица терминов (`terms-ru.md` §5).

### RU-04. Жаргон и англицизмы — по классам
**STE:** 1.10, 1.12
**Правило.** Три класса слов. Класс A — технические существительные без короткого русского эквивалента (деплой, таймаут): в текстах для инженеров разрешены везде, одно написание. Для внешних пользователей и UI-строк — только слова класса A, которые есть в интерфейсе продукта. Класс B — глаголы-кальки (запушить, замержить): разрешены в чате, тикетах и PR, в документации → русский глагол. Класс C — сниженный жаргон (костыль, флапает): только чат и только при однозначности. «Выкатить», «откатить» — класс A во всех жанрах. Списки слов и замены — `terms-ru.md` §1.
**Почему.** Сленг понимает только своя команда. Новичок, внешний читатель и переводчик — нет. У глагола-кальки нет нормативной формы (см. RU-05).
**Ищите.**
- Приставка «за-» + английская основа: запушить, заасайнить, зареджектить, заюзать.
- Бытовые слова о технике: тачка, морда, костыль, кубер, репа. Транслит — RU-07, RU-10.
- Один шаг назван и «запушьте», и «отправьте» в одном тексте.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Запушьте ветку, дождитесь апрува PR и задеплойте сервис в прод.» → Хорошо: «Отправьте ветку в репозиторий. Дождитесь одобрения PR. Разверните сервис в проде.» — два глагола класса B и «апрув» заменены русскими словами. Три действия — три предложения.
- [тикет; переписывание] Плохо: «Морда флапает после выкатки, кубер не видит ноду.» → Хорошо: «Фронтенд после выкатки то отвечает, то нет. Kubernetes не видит ноду.» — «морда», «флапает», «кубер» — класс C и транслит. «Флапает» значит «работает с перебоями», поэтому «то отвечает, то нет». «Выкатка» и «нода» — класс A, остаются.
- [PR; переписывание] Плохо: «Пофиксил костыль в ретраях и дропнул старую таблицу.» → Хорошо: «Я исправил временное решение в ретраях и удалил старую таблицу.» — класс C заменён нейтральными словами. «Я» в PR допустимо (см. RU-12).
**Исключения.** Глоссарий проекта переопределяет класс слова. Цитаты чужих сообщений и логов не переписывайте. Класс B в чате — по одному глаголу на операцию, без чередования «запушьте/отправьте».

### RU-05. Не образовывать глаголы от терминов
**STE:** 1.2, 1.7, 3.1
**Правило.** Термин-существительное остаётся существительным. Действие — обычный глагол + термин: не «забэкапьте», а «сделайте бэкап». Не «затегайте», а «поставьте тег». Не «отревьюйте», а «сделайте ревью». Если у действия есть русский глагол — используйте его: «зарелизьте» → «выпустите релиз», «зареббейзенная ветка» → «перебазированная ветка».
**Почему.** У самодельного глагола нет нормативной формы: «забэкапьте», «забекапьте», «забэкапте» — три написания одного слова. Такие формы не переводятся и не ищутся.
**Ищите.**
- Приставка + термин + «-ить/-нуть»: забэкапить, затегать, законфигурить, зарелизить, заскейлить, отревьюить, перевыкатить.
- Прилагательные от терминов: замерженный, задеплоенный, зареббейзенный, зафейленный.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Забэкапьте базу и затегайте коммит перед релизом.» → Хорошо: «Перед релизом сделайте бэкап базы. Перед релизом поставьте тег на коммит.» — «бэкап» и «тег» остались существительными. Действие названо обычным глаголом, порядок действий не добавлен.
- [тикет; переписывание] Плохо: «Заскейльте воркеры до пяти инстансов и перевыкатите сервис.» → Хорошо: «Задайте 5 инстансов воркера. Выкатите сервис заново.» — «заскейлить до пяти» → «задайте 5»: направление масштабирования в исходнике не задано, поэтому не «увеличьте». «Перевыкатить» → «выкатить заново».
- [PR; переписывание] Плохо: «Ветка зареббейзена на main, конфиг законфигурен под тестовый стенд.» → Хорошо: «Ветка перебазирована на main. Конфиг настроен для тестового стенда.» — состояние выражено обычным кратким причастием. Термин «конфиг» остался существительным.
**Исключения.** Глаголы класса B — кальки («запушьте», «замержите») и глаголы от терминов («забэкапьте», «затегайте») — допустимы в чате, тикете и описании PR (см. RU-04). В документации — глагол + термин (`terms-ru.md` §1). Словарные глаголы на «-ировать»: «логировать», «кешировать», «мигрировать», «валидировать». Технические глаголы «выкатить», «откатить».

### RU-06. Короткий термин
**STE:** 1.9, 2.2
**Правило.** Термин — не длиннее трёх знаменательных слов. Если объект однозначно задан идентификатором (имя файла, сервиса, таблицы, переменной), пишите идентификатор вместо описания. Официальное название длиннее трёх слов пишите полностью один раз, затем «(далее — …)» или официальную аббревиатуру, а термины из 1–3 слов не сокращайте. Счёт дефисных слов и идентификаторов — `counting.md`.
**Почему.** Описание из шести слов читатель разбирает заново при каждом упоминании и не может найти поиском. Самодельная аббревиатура непонятна вне команды.
**Ищите.**
- Цепочки из четырёх и более существительных: «обработчик очереди отложенных уведомлений заказов».
- Обороты «файл конфигурации параметров …», «переменная окружения, отвечающая за …».
- Самодельные сокращения названий продуктов и понятий: «ПРка», «дока». Самодельные аббревиатуры (ЛК, ПМ) — RU-10.
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Откройте конфигурационный параметр лимитов рейт-лимитера `RATE_LIMITER_LIMITS`.» → Хорошо: «Откройте конфиг `RATE_LIMITER_LIMITS`.» — идентификатор уже задаёт объект однозначно. Описание из четырёх слов лишнее.
- [инструкция; переписывание] Плохо: «Запустите обработчик очереди отложенных уведомлений.» → Хорошо: «Запустите воркер отложенных уведомлений.» — только по глоссарию проекта, где «воркер» — обработчик очереди. Без глоссария оставьте описание и задайте вопрос. Четыре существительных подряд → термин из трёх слов.
- [тикет; переписывание] Плохо: «Проверьте, что НТ подтверждён в ЛК.» → Хорошо: «Проверьте, что номер телефона подтверждён в личном кабинете.» — только если глоссарий проекта расшифровывает НТ и ЛК. Без глоссария — «<уточните: НТ, ЛК>». Термины из двух слов не сокращают.
**Исключения.** Идентификатор любой длины — одно слово: `RATE_LIMITER_LIMITS`, `PROJ-1234`. Официальные названия продуктов не сокращайте и не переписывайте: «Платформа данных», не «ПД». Аббревиатура из белого списка (см. RU-10).

### RU-07. Единая орфография
**STE:** 8.6 (1.14 и GR-8 — нет аналога, см. `ste-mapping.md`)
**Правило.** Буква «ё» — всегда в порождаемом тексте. Одно написание заимствования на весь текст. Имена продуктов, код и идентификаторы — латиницей, без склонения и апострофа. Если нужен падеж, добавьте родовое слово: «в базе Redis», «в ветке main». Цитаты интерфейса и логов — дословно, без перевода. Таблица написаний и латиница — `terms-ru.md` §2–3.
**Почему.** Два написания — два слова для поиска и для читателя. «Vault'е» и «в постгресе» не найти поиском. Переведённая строка лога не совпадёт с реальной, и читатель её не найдёт.
**Ищите.**
- Пары написаний: кеш/кэш, бэкенд/backend/бекенд, таймаут/тайм-аут.
- Апостроф после латиницы: Vault'е, Docker'ом. Транслит имён продуктов: постгрес, кубер, гит, редис.
- «Е» вместо «ё»: все/всё, удален, отменен. Переведённые надписи кнопок и строки логов.
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Очистите кеш. После перезапуска кэш прогреется сам, а старые записи удалятся.» → Хорошо: «Очистите кеш. После перезапуска кеш прогреется сам. Старые записи удалятся.» — два написания одного термина сведены к одному.
- [инструкция; переписывание] Плохо: «Секреты храните в Vault'е, а конфиг — в GitLab'е.» → Хорошо: «Храните секреты в хранилище Vault, а конфиг — в GitLab.» — апостроф убран. Родовое слово даёт падеж без склонения латиницы.
- [wiki; переписывание] Плохо: «В логе появится строка «соединение сброшено другой стороной».» → Хорошо: «В логе появится строка <уточните: точный текст строки из лога>.» — переведённую цитату лога по памяти не восстанавливайте: плейсхолдер и вопрос автору. Если исходная строка есть в логах или у автора, вставьте её дословно: `connection reset by peer`.
**Исключения.** Внутри цитат, кода и идентификаторов ничего не меняйте, включая «е/ё» и написание. Глоссарий проекта переопределяет таблицу написаний. Устоявшиеся кириллические имена продуктов («Платформа данных») пишите как в глоссарии.

### RU-08. Ложные друзья и кальки
**STE:** GR-5
**Правило.** Не переносите значение английского слова на похожее русское. actual → «фактический», не «актуальный». functionality → «функциональность» или имя функции, не «функционал». expertise → «опыт» или «компетенция», не «экспертиза». original → «исходный», не «оригинальный». Если английский термин нужен — заимствуйте его единообразно и добавьте в таблицу терминов (`terms-ru.md` §5). Полный список — `stop-words-ru.md` §11.
**Почему.** Ложный друг звучит по-русски и меняет смысл незаметно: «актуальное значение» читают как «важное сейчас», «экспертизу» — как процедуру. При обратном переводе получается другое слово.
**Ищите.**
- Актуальный, аккуратный (accurate → «точный»), функционал, экспертиза.
- Адекватный (adequate → «достаточный», только с числом или критерием, см. RU-09), комплексный (complex → «сложный»).
- Оригинальный (в значении «исходный»), контролировать (в значении «управлять»), «сущность» вне моделей данных (entity → «объект», «запись»).
- Кальки-обороты: «в терминах» (in terms of → «с точки зрения»), «на регулярной основе» (→ «регулярно»), «имеет смысл» (→ «рекомендуем», слово «стоит» запрещено, см. RU-15).
**Плохо → Хорошо.**
- [тикет; переписывание] Плохо: «Сравните ожидаемое и актуальное значение лимита в базе.» → Хорошо: «Сравните ожидаемое и фактическое значение лимита в базе.» — калька с actual value. В паре с «ожидаемым» подходит только «фактическое».
- [PR; переписывание] Плохо: «Функционал экспорта временно отключён: у команды нет экспертизы в Kubernetes.» → Хорошо: «Экспорт временно отключён: у команды нет опыта работы с Kubernetes.» — «функционал» → имя функции, «экспертиза» (expertise) → «опыт».
- [README; написание] Плохо: «Скрипт восстанавливает оригинальный конфиг из бэкапа.» → Хорошо: «Скрипт восстанавливает исходный конфиг из бэкапа.» — original → «исходный». По-русски «оригинальный» значит «необычный».
**Исключения.** Слово в своём русском значении: «актуальная версия документа» (та, которая действует сейчас), «экспертиза» как официальное заключение. Термин глоссария («консистентность» в контексте БД) остаётся.

### RU-09. Без размытых слов и оценок без критерия
**STE:** 4.1 (сравнение без второго члена — RU-only расширение)
**Правило.** Удалите усилитель, смягчитель и вводное слово или замените его числом, условием, именем: «очень быстро» → «за 50 мс», «при определённых условиях» → «если …». Замены — `stop-words-ru.md` §6–7. Сравнение — только с явным вторым членом и числом: «на 30 % быстрее версии 1.9». Оценки без критерия («оптимальный», «достаточно», «наиболее», «лучше + инфинитив») не используйте. В режиме переписывания недостающее число не выдумывайте: «<уточните>» и вопрос (см. RU-00).
**Почему.** Размытое слово обещает информацию и не даёт: читатель не может ни принять решение, ни проверить утверждение. «Очевидно» унижает того, кому не очевидно. Запрет оценок без критерия — расширение RU-only: редполитики и практика ste-ru.
**Ищите.**
- Усилители и смягчители: очень, крайне, весьма, довольно, достаточно, практически, значительно, существенно, примерно (без допуска).
- Заместители без числа: некоторые, определённые, соответствующие, различные, ряд, многие.
- Вводные: как правило, в принципе, по сути, собственно, очевидно, естественно, разумеется.
- Оценки: оптимальный, максимально, наиболее, самый. Сравнительная степень без «чем».
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Естественно, перед миграцией желательно сделать бэкап.» → Хорошо: «Перед миграцией рекомендуем сделать бэкап.» — «естественно» удалено. «Желательно» → «рекомендуем»: сила утверждения сохранена (RU-00).
- [README; написание] Плохо: «Новая версия работает заметно быстрее и использует оптимальный размер пула.» → Хорошо: «Версия 2.0 обрабатывает запрос за 40 мс вместо 120 мс в версии 1.9. Размер пула — 20 соединений.» — названы оба члена сравнения и числа. Автор в режиме написания их знает.
- [тикет; переписывание] Плохо: «Некоторые запросы иногда падают с ошибкой, скорее всего из-за таймаута.» → Хорошо: «Часть запросов завершается с ошибкой <уточните: какие и как часто>. Вероятная причина — таймаут.» — «некоторые» и «иногда» → плейсхолдер и вопрос. Хедж сохранён словом «вероятная».
**Исключения.** «Примерно» или «около» с объявленным допуском: «примерно 1000 RPS (±10 %)». «Например» перед примером. Хедж в тикете или чате, если рядом сказано, как проверить. В режиме переписывания хедж исходника сохраняйте (RU-00).

### RU-10. Без сокращений, аббревиатуры по белому списку
**STE:** 4.2, GR-6, 2.2, 8.6
**Правило.** Графические и латинские сокращения («т. е.», «напр.», «etc.», «и/или») не используйте. «И т. д.» после «например», «включая», «в том числе» удалите: список уже открыт. Если список подан как полный, вместо «и т. д.» пишите «<уточните, что ещё>»: дописать список может только автор. В описании пишите «то есть» и «например» словами, в шаге вместо «то есть» — тире или скобки. «И/или» → «или». Если важно, что допустимы оба варианта, — «или оба». «См.», «рис.», «табл.» — только внутри скобочных ссылок: «(см. раздел 3)». Аббревиатура без расшифровки — только из белого списка, остальные расшифруйте при первом упоминании и дальше пишите одинаково, латиницей. Белый список и таблица замен — `terms-ru.md` §4, `stop-words-ru.md` §12.
**Почему.** «И т. д.» означает, что автор не дописал список: читатель не знает, что ещё входит. «И/или» — два утверждения в одном. Аббревиатура без расшифровки понятна только своему кругу и не ищется.
**Ищите.**
- Графические сокращения: «т. е.», «т.е.», «т. д.», «т. п.», «и др.», «пр.», «напр.», «см.» вне скобок.
- Латинские: «e.g.», «i.e.», «etc.», «vs.», «a.k.a.». Составное «и/или».
- Аббревиатуры из 2–4 заглавных букв вне белого списка без расшифровки. Транслит аббревиатур: апи, джейсон, пиар, ци.
**Плохо → Хорошо.**
- [README; переписывание] Плохо: «Сервис поддерживает разные форматы, напр. JSON, YAML и т. д.» → Хорошо: «Сервис поддерживает разные форматы, например JSON и YAML.» — «например» уже говорит, что список открыт. «И т. д.» ничего не добавляет. Без «например» здесь стоял бы «<уточните, что ещё>».
- [инструкция; переписывание] Плохо: «Проверьте TTL и RPS в дашборде и/или в логах.» → Хорошо: «Проверьте время жизни (TTL) и число запросов в секунду (RPS) в дашборде или в логах.» — аббревиатуры вне белого списка расшифрованы. Объект TTL (ключ, запись, сессия) в исходнике не назван, поэтому не добавлен (RU-00). «И/или» → «или»: русское «или» допускает оба варианта.
- [wiki; переписывание] Плохо: «Параметр задаёт TTL, т.е. время жизни записи в кеше, см. раздел «Кеш».» → Хорошо: «Параметр задаёт время жизни записи в кеше (TTL). Подробности — в разделе «Кеш».» — расшифровка стала основным текстом, аббревиатура ушла в скобки. Ссылка — отдельным предложением.
**Исключения.** Единицы измерения: мс, с, МБ, ГБ. Названия продуктов и протоколов: HTTP, gRPC, YAML. «См.» в скобочной ссылке. Аббревиатура из глоссария проекта. Внутри цитат и кода — как в источнике.

## B. Глаголы

### RU-11. Действие — глаголом
**STE:** 3.7, 3.5, 1.13
**Правило.** Называйте действие глаголом. Не расщепляйте сказуемое: «выполнить проверку» → «проверьте», «производить запись» → «записывает». Отглагольное существительное оставляйте только как термин-предмет («миграция» — файл, «сборка» — артефакт) и в заголовках. «Сделайте + термин» пишите, только если у термина нет глагольной пары: «сделайте бэкап».
**Почему.** Глагол-пустышка несёт только грамматику, а смысл уходит в существительное. Предложение растёт, исполнитель и время действия исчезают.
**Ищите.** «Осуществлять», «производить», «выполнять», «проводить», «обеспечивать», «реализовывать» + существительное на -ение, -ание, -ка, -ция. «Является», «представляет собой», «имеется». «Приводит к», «наличие», «отсутствие». Условие через «при + отглагольное» — RU-26.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Выполните проверку прав доступа к базе `orders_db`.» → Хорошо: «Проверьте права доступа к базе `orders_db`.» — «выполнить проверку» → «проверьте».
- [README; переписывание] Плохо: «Сервис `notifications` осуществляет отправку событий в очередь.» → Хорошо: «Сервис `notifications` отправляет события в очередь.» — расщеплённое сказуемое заменено глаголом.
**Исключения.** Термины-предметы: «настройки» (набор параметров), «подключение» (объект в пуле), «миграция» (файл), «сборка» (артефакт). Заголовки и подписи кнопок: «Настройка», «Загрузка». Устойчивые сочетания «выполните команду», «выполните запрос».

### RU-12. Действительный залог с реальным исполнителем
**STE:** 3.4, 3.6
**Правило.** Исполнитель действия — подлежащее: «Сервис сохраняет счётчик». Если исполнитель — читатель, пишите императив. Пассив «был/будет + причастие», «-ся» с агентом в творительном падеже, «подлежит» и неопределённо-личные формы («доступ выдают») — только в описании. И только когда исполнитель неизвестен. Безличные модальные слова — по RU-15. «-ся» без агента допустим для процесса, который идёт сам: «Кеш очищается раз в час». Исполнителя не выдумывайте (RU-00).
**Почему.** Пассив прячет исполнителя. Читатель инструкции не понимает, действовать ему или ждать. При переводе деятель теряется окончательно.
**Ищите.** «Был/были» + причастие на -н/-т, «будет» + «-но/-ны», «должен быть» или «может быть» + причастие. Творительный падеж деятеля («системой», «скриптом», «дежурным») рядом с глаголом на -ся или причастием. «Подлежит». Глагол в 3-м лице множественного числа без подлежащего («хранят», «выдают», «починили»).
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Лимиты читаются сервисом `rate-limiter` из конфига `RATE_LIMITER_LIMITS` при старте.» → Хорошо: «При старте сервис `rate-limiter` читает лимиты из конфига `RATE_LIMITER_LIMITS`.» — агент из творительного падежа стал подлежащим.
- [инструкция; переписывание] Плохо: «Перед деплоем вам необходимо отозвать старые ключи.» → Хорошо: «Перед деплоем отзовите старые ключи.» — адресат назван в исходнике («вам»), поэтому императив. Требование-состояние без исполнителя («ключи должны быть отозваны») — предусловие: пишите «убедитесь, что старые ключи отозваны» или спросите, кто отзывает.
- [тикет; переписывание] Плохо: «Ошибка в подсчёте скидки была исправлена мной, я запланировал выкатку на среду.» → Хорошо: «Я исправил ошибку в подсчёте скидки. Я запланировал выкатку на среду.» — «мной» стал подлежащим: в тикете первое лицо допустимо. Род глагола «исправил» взят из «запланировал» в исходнике, не угадан (RU-00).
**Исключения.** Состояние без вспомогательного глагола: «Порт 443 открыт», «Заказ отменён». Описание с неизвестным исполнителем: «Во время передачи данные были повреждены». Строки интерфейса и цитаты: «Файл не найден». Глаголы-связки: «называется», «находится», «состоит из». В PR, тикете и чате «я» и «мы» допустимы, если автор — реальный исполнитель.

### RU-13. Разрешённые формы глагола
**STE:** 3.1, 3.2, 3.3, 3.5, 1.4
**Правило.** Используйте повелительное наклонение, настоящее, прошедшее и будущее время. Инфинитив — только после «чтобы», «можно», «должен» и в подписях кнопок, заголовках, названиях задач (RU-24). Страдательное причастие прошедшего времени — только как определение или состояние: «сохранённый конфиг», «сервис остановлен». Не используйте деепричастия, действительные причастия, причастные обороты и сослагательное наклонение («нужно было бы»). В инструкциях причастий нет. Деепричастие — только для одновременных действий: «Удерживая Shift, нажмите…». В описаниях действительный причастный оборот → «который…» или отдельное предложение.
**Почему.** Причастие сворачивает придаточное в одно слово, и читатель ищет, к какому существительному оно относится. Деепричастие сливает два действия и прячет связь между ними.
**Ищите.** Суффиксы -ущий/-ющий/-ащий/-ящий, -вший, -емый/-имый с зависимыми словами. Суффиксы -я/-а, -в/-вши/-ясь после глагольной основы («используя», «нажав», «подключившись»). Запятая, за которой сразу идёт причастие. «Бы», «было бы».
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Дождавшись зелёного статуса CI, слейте PR в `main`.» → Хорошо: «Дождитесь зелёного статуса CI. Затем слейте PR в `main`.» — деепричастие скрывало отдельный шаг.
- [README; переписывание] Плохо: «Скрипт, удаляющий устаревшие сессии, запускается раз в сутки.» → Хорошо: «Скрипт удаляет устаревшие сессии. Он запускается раз в сутки.» — причастный оборот → отдельное предложение. «Он» относится к единственному существительному мужского рода (RU-21). Исполнитель запуска не выдуман.
- [PR; переписывание] Плохо: «Стоило бы добавить ретраи в клиент `notifications`.» → Хорошо: «Предлагаю добавить ретраи в клиент `notifications`.» — сослагательное наклонение заменено прямым предложением. Сила высказывания сохранена (RU-00).
**Исключения.** Причастия-термины: «входящий запрос», «выделенный сервер», «удалённый репозиторий», «зарезервированное слово». Одиночное страдательное причастие перед существительным: «сохранённый конфиг». Формы, которые стали предлогами: «начиная с версии 2.0», «включая», «спустя».

### RU-14. Вид глагола в императиве
**STE:** нет аналога (RU-only), связано с 3.2, 5.3
**Правило.** Разовый шаг — совершенный вид: «Откройте», «Запустите», «Сохраните». Повторяющееся или длящееся действие — несовершенный: «Проверяйте логи каждый день», «Держите ветку актуальной». Запрет — «не + несовершенный вид»: «Не удаляйте», «Не запускайте». Опора — Розенталь и практика ste-ru.
**Почему.** Вид меняет смысл команды. «Нажимайте» читается как «жмите много раз», «Проверяйте» — как «постоянно». «Не удалите» — предостережение от случайности, а не правило.
**Ищите.** Императив несовершенного вида в нумерованном шаге без слов «каждый», «регулярно», «всегда», «пока»: «нажимайте», «открывайте», «запускайте». «Не» + совершенный вид: «не удалите», «не запустите». «Всегда», «каждый раз» + совершенный вид.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Запускайте миграцию командой `make migrate`.» → Хорошо: «Запустите миграцию командой `make migrate`.» — разовый шаг — совершенный вид.
- [инструкция; переписывание] Плохо: «Не удалите ветку `release` до конца регресса.» → Хорошо: «Не удаляйте ветку `release` до конца регресса.» — запрет — несовершенный вид. Так пишут, когда путают запрет с предостережением.
- [wiki; переписывание] Плохо: «Обновите зависимости раз в неделю.» → Хорошо: «Обновляйте зависимости раз в неделю.» — повторяющееся действие — несовершенный вид.
**Исключения.** Глаголы без видовой пары или с одной формой в обоих значениях: «используйте», «учитывайте». Предостережение от случайного действия: «Не перепутайте порты» — допустимо в предупреждении. Рекомендуем положительную команду: «Проверьте номера портов».

### RU-15. Модальность в два уровня
**STE:** 5.3, словарь STE (must, can), RU-00
**Правило.** Два уровня. Обязательно: императив читателю или «должен + глагол» о системе и требовании. Возможно: «можно» читателю, «может» о системе — только в значении способности. Не используйте «следует», «необходимо», «требуется», «рекомендуется», «желательно», «стоит», «целесообразно», «допускается», «обязан», «вправе». «Нужен/нужна/нужно» — только как прилагательное для предусловий: «Нужен доступ к Vault». «Следует» и «не следует» в нумерованном шаге инструкции → императив и «Не + императив» (по умолчанию). В описании, wiki и совете → «Рекомендуем» и «Не рекомендуем». При сомнении задайте вопрос автору. «Рекомендуется», «желательно», «стоит» → «Рекомендуем» всегда. «Может» + нежелательное событие («может упасть»): в режиме переписывания хедж сохраняйте. В режиме написания предпочитайте условие «если …» или долю случаев. Без данных пишите «может» и задайте вопрос автору. Вероятность не превращайте в факт. При переписывании силу не меняйте: «рекомендуется X» → «Рекомендуем X», не «Сделайте X» (RU-00).
**Почему.** Русская шкала обязательности размазана по десятку слов, и авторы используют их как синонимы. «Следует» одни читают как требование, другие как совет. «Может» значит и разрешение, и способность, и вероятность.
**Ищите.** «Следует», «необходимо», «нужно + инфинитив», «надо», «требуется», «рекомендуется», «желательно», «стоит», «целесообразно», «допускается», «обязан», «вправе». Два модальных слова подряд («обязательно нужно»). В режиме написания — «может» + нежелательное событие («может упасть») без условия и доли случаев.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «После смены лимитов необходимо перезапустить воркер.» → Хорошо: «После смены лимитов перезапустите воркер.» — «необходимо + инфинитив» никому не адресовано. Императив снимает вопрос.
- [спецификация; переписывание] Плохо: «Сервис `orders` обязан отвечать на `/ping` в течение 1 с.» → Хорошо: «Сервис `orders` должен отвечать на `/ping` за 1 с или быстрее.» — требование к системе — «должен». «В течение 1 с» — предел, поэтому «за 1 с или быстрее» (`stop-words-ru.md` §4).
- [README; переписывание] Плохо: «Рекомендуется включить кеш для эндпоинта `/v1/orders`.» → Хорошо: «Рекомендуем включить кеш для эндпоинта `/v1/orders`.» — совет остался советом. Последствие не выдумано (RU-00).
**Исключения.** Спецификации по RFC 2119 с объявленной шкалой «ДОЛЖЕН / СЛЕДУЕТ / МОЖЕТ»: шкалу описывают в начале документа и применяют строго. Юридические тексты, где «обязан» и «вправе» — термины.

## C. Предложения

### RU-16. Длина предложения
**STE:** 4.1, 5.1, 6.3, 8.4, 8.5, 8.6, 8.7
**Правило.** Шаги и предупреждения — не длиннее 20 слов, описания и примечания — не длиннее 25. Ориентир средней длины: 12–15 слов в инструкциях, 15–18 в описаниях. Длинное предложение делите по мыслям, а не удаляйте слова (RU-20). Что считать одним словом и одним предложением — `counting.md`.
**Почему.** Длинное предложение читатель разбирает на части сам и держит в памяти незакрытые конструкции. Короткое предложение переводится и проверяется отдельно.
**Ищите.** Более 20 или 25 слов по правилам `counting.md`. Скобка длиннее лимита. Цепочки союзов и запятых — RU-17.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо (22 слова): «Перед выкаткой проверьте, что тесты в CI зелёные и миграции применены на тестовом стенде, потому что без этого релизный пайплайн не стартует.» → Хорошо: «Перед выкаткой проверьте, что тесты в CI зелёные и миграции применены на тестовом стенде. Иначе релизный пайплайн не стартует.» — 14 и 5 слов. Проверка и последствие разведены по предложениям.
- [wiki; переписывание] Плохо: «Сервис `orders` хранит заказы в базе `orders_db`, а счётчики по каждому пользователю — в Redis, откуда их раз в минуту забирает `rate-limiter`, чтобы пересчитать лимиты.» → Хорошо: «Сервис `orders` хранит заказы в базе `orders_db`. Сервис `orders` хранит счётчики по каждому пользователю в Redis. Раз в минуту `rate-limiter` забирает счётчики из Redis, чтобы пересчитать лимиты.» — три мысли — три предложения. Все факты и цель «чтобы» сохранены.
**Исключения.** Заголовки, код, таблицы, цитаты логов — не предложения, в лимиты не входят. Если предложение нельзя разделить без потери связи, перестройте его: глагол вместо отглагольного (RU-11), условие первым (RU-26). Слова не вычёркивайте (RU-20).

### RU-17. Одна мысль на предложение
**STE:** 4.1, 4.4, 6.1
**Правило.** Одно предложение — одна мысль, не более одного придаточного, без цепочек «который…, что…, при этом…». Причину пишите отдельным предложением или через «потому что» в описании. Цель и условие перед командой — RU-26. Связки: и, но, затем, потом, после этого, поэтому, в результате, например, иначе. Их можно ставить в начало предложения. Не используйте «при этом», «однако» (→ «но»), «таким образом», «в связи с этим», «в свою очередь», «а также», «причём». «Кроме того» и «также» в начале предложения — сигнал новой темы (RU-31).
**Почему.** Каждый ярус придаточных — ещё одна незакрытая конструкция в памяти читателя. Канцелярская связка присоединяет факт, но не называет связь: условие это, исключение или одновременность.
**Ищите.** Два и более союза из набора «что, чтобы, который, так как, поскольку, при этом, причём» в одном предложении. Три и более запятых. «А также», «однако», «кроме того», «в том числе». «То есть» в шаге — пояснение вынесите в скобки или отдельным предложением (RU-10, `stop-words-ru.md` §12). «И» между двумя командами.
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Сервис `notifications` кеширует шаблоны писем в Redis, при этом кеш живёт 10 минут, однако при недоступности Redis сервис ходит за шаблонами напрямую.» → Хорошо: «Сервис `notifications` кеширует шаблоны писем в Redis. Кеш живёт 10 минут. Но если Redis недоступен, сервис запрашивает шаблоны напрямую.» — три факта — три предложения. «Однако» → «но».
- [инструкция; переписывание] Плохо: «Остановите воркер, а также очистите очередь `retry`, причём до перезапуска.» → Хорошо: «Остановите воркер. Очистите очередь `retry` до перезапуска.» — «а также» и «причём» прятали второе действие и его условие.
- [PR; переписывание] Плохо: «Добавил ретраи в клиент, таким образом, таймауты `orders` больше не ломают запрос, в связи с этим убрал обходное решение в обработчике.» → Хорошо: «Я добавил ретраи в клиент. В результате таймауты `orders` больше не ломают запрос. Поэтому я убрал обходное решение в обработчике.» — канцелярские связки заменены простыми.
**Исключения.** Одно придаточное «что» после глаголов проверки: «Убедитесь, что…», «Сервис проверяет, что…». «И» между двумя короткими однородными объектами: «Проверьте порты и адреса». Одновременные действия в одном шаге (см. RU-13).

### RU-18. Прямой порядок слов и скобки
**STE:** 8.3, порядок слов — нет аналога (RU-only)
**Правило.** Пишите в прямом порядке: подлежащее → сказуемое → дополнение → обстоятельства. Условие и время — впереди (RU-26), сразу за ними — подлежащее и сказуемое. Не разрывайте подлежащее и сказуемое вставкой длиннее трёх слов. Если именительный и винительный падежи совпадают («сервер вызывает клиент»), перестройте предложение или добавьте предлог. Скобки — только для ссылок «(см. раздел 3)», аббревиатур после полного названия, коротких пояснений и альтернатив. Команды, условия и оговорки в скобки не прячьте — выносите их отдельным предложением. Разрешённые скобки: ссылка «(см. раздел 3)», номер шага «(см. шаг 3)», аббревиатура после полного названия, короткое пояснение, альтернатива «(JSON или YAML)». Вместо «(ы)» и «(и)» пишите множественное число.
**Почему.** Свободный порядок слов уводит подлежащее и глагол в конец, и читатель до последнего слова не знает, кто что делает. Неноситель и переводчик не распознают инверсию. Читатель пропустит команду в скобках. Прямой порядок слов — RU-only: правило ste-ru, нормативная опора не сверена.
**Ищите.** Предложение начинается с двух и более обстоятельств подряд. Сказуемое раньше подлежащего («задаёт лимит администратор»). Между подлежащим и сказуемым более трёх слов. Глагол в самом конце длинного предложения. Совпадение именительного и винительного падежей («ответ формирует шлюз»). Скобка с императивом или с «если». «(ы)», «(и)».
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Запись в таблицу `audit` после каждого запроса делает сервис `orders`.» → Хорошо: «Сервис `orders` пишет в таблицу `audit` после каждого запроса.» — подлежащее и сказуемое подняты вперёд. «Делает запись» → «пишет» (RU-11).
- [инструкция; переписывание] Плохо: «Выкатите релиз (если дежурный одобрил чеклист).» → Хорошо: «Если дежурный одобрил чеклист, выкатите релиз.» — условие вынуто из скобок и поставлено первым (RU-26).
**Исключения.** Короткие предложения до пяти слов, где инверсия однозначна: «Осталось два шага». Заголовки, подписи, вопросы в переписке. Скобки для номера шага и ссылки: «(см. шаг 3)».

### RU-19. Именные группы
**STE:** 2.1, 2.2, 8.2, 8.7
**Правило.** После главного слова — не более двух родительных падежей подряд: «таймаут ответа сервиса» — предел. Перед существительным — не более двух определений. Длинную цепочку разбивайте глаголом («проверить, действует ли подписка»), предлогом («статус подписки у пользователя»), прилагательным или «который». Термин из глоссария и дефисное слово (API-ключ, веб-сервер, HTTP-запрос) — одно слово. Дефис ставьте по орфографии: «веб-сервер», «5-секундный», «T-образный». Дефис — не тире (см. RU-23).
**Почему.** Цепочка родительных читается только с конца, а связи между звеньями неоднозначны: «проверка статуса подписки пользователя» — проверяем статус или подписку? Слова с одинаковыми окончаниями сливаются в шум.
**Ищите.** Три и более существительных подряд без предлогов и глаголов. Два и более слов подряд на -ия/-ии/-ения/-ования. «Результат … выполнения …», «процесс … обработки …», «параметры … конфигурации …». «Сервиса», «системы», «данных» в конце длинной группы. «Веб сервер», «API ключ» без дефиса.
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Лог результатов проверки лимитов запросов пользователей пишется в таблицу `audit`.» → Хорошо: «Лог с результатами проверки лимитов на запросы пользователей пишется в таблицу `audit`.» — предлоги «с» и «на» разбили цепочку из пяти родительных. «Лог» сохранён, исполнитель не выдуман.
- [README; переписывание] Плохо: «Добавьте SSH ключ в настройки CI раннера.» → Хорошо: «Добавьте SSH-ключ в настройки CI-раннера.» — дефис показывает, что аббревиатура и слово — один термин. Каждое дефисное слово считается одним.
- [инструкция; переписывание] Плохо: «Используйте внутренний минимальный подписанный образ базового контейнера.» → Хорошо: «Используйте образ базового контейнера. Образ должен быть внутренним, минимальным и подписанным.» — три определения перед существительным вынесены в отдельное предложение. «Должен» о требовании допустим (RU-15).
**Исключения.** Устоявшиеся термины из трёх и более существительных: «система управления базами данных», «журнал аудита доступа». Пути и ключи конфига — кодом: `db.pool.max_size`. Официальные названия и должности.

### RU-20. Полные предложения
**STE:** 4.2, GR-1
**Правило.** Не выбрасывайте слова ради короткого предложения. Пишите глагол-действие, подлежащее — и в условии «если …» тоже, союз «что» после «убедитесь», «проверьте», «покажите», существительное при числе и единицу измерения. Телеграфный стиль запрещён: полное предложение из шести слов понятнее обрубка из трёх. «Что» — факт, «чтобы» — цель: «проверьте, что сервис отвечает», «чтобы сервис отвечал, …». В предупреждении «иначе» без подлежащего («иначе — потеря данных») разверните в полное предложение с существительным: «Иначе миграция ломает схему».
**Почему.** Каждое пропущенное слово — работа, которую вы перекладываете на читателя. Он достраивает пропущенное по-своему. Союз «что» показывает границу главной и придаточной частей, а при переводе он обязателен.
**Ищите.** Предложение без глагола длиннее трёх слов. Тире между существительным и предложной группой («логи — в `/var/log`»). Число без единицы. «Если включён», «если нет» без подлежащего. «Убедитесь, сервис…» без «что». «Только после», «только через» без глагола. Прошедшее время 3-го лица без подлежащего («упало», «починили»).
**Плохо → Хорошо.**
- [тикет; переписывание] Плохо: «Таймаут 30, ретраев 3, потом в DLQ.» → Хорошо: «Таймаут — 30 <уточните единицу: с или мс>. Число ретраев — 3. После последнего ретрая <уточните: что> уходит в DLQ.» — восстановлены глагол и подлежащие. Единица и объект третьего предложения не выдуманы, а запрошены (RU-00).
- [инструкция; переписывание] Плохо: «Если пусто, заполните `owner` в манифесте.» → Хорошо: «Если поле `owner` в манифесте пустое, заполните его.» — в условии восстановлено подлежащее.
- [инструкция; переписывание] Плохо: «Убедитесь: воркер остановлен. Только потом чистите очередь.» → Хорошо: «Убедитесь, что воркер остановлен. Только после этого очистите очередь.» — восстановлен союз «что». «Чистите» → «очистите» (см. RU-14).
**Исключения.** Таблицы и списки параметров («Порт: 8080»). Определения через тире: «Redis — кеш». Заголовки, подписи кнопок, цитаты логов. Второе из двух параллельных коротких предложений, если глагол назван в первом. В описании PR и в чате прошедшее время без «я» допустимо, если исполнитель — автор сообщения: «Добавил кеш».

### RU-21. Однозначная референция
**STE:** 4.5, GR-2, GR-3, GR-4
**Правило.** Повторяйте существительное вместо «он/она/оно/они», если между местоимением и его существительным стоит другое существительное того же рода или местоимение начинает предложение. «Это» в начале предложения — только с существительным: «Эта проверка…». «Данный», «указанный», «вышеупомянутый», «настоящий», «соответствующий», «таковой» → «этот» или само существительное. «Последний» (второй из двух) не используйте. «Который» ставьте сразу после своего слова. «Свой» — только к подлежащему. Каждое «с + творительный падеж» проверяйте на три прочтения: «имеющий», «вместе с», «при помощи». Инструмент пишите творительным падежом без предлога («утилитой pg_dump»), «с» — только в значении «вместе с».
**Почему.** Русское местоимение согласуется по роду, и при двух существительных одного рода «он» неразрешим. «Это» может указывать на слово, на ситуацию или на весь абзац.
**Ищите.** «Он/она/они/его/её/их» после двух существительных одного рода. «Это/этого» в начале предложения без существительного. «Данный», «указанный», «вышеуказанный», «последний», «тот же». «Который» через два существительных от своего слова. «С + творительный» рядом с командой.
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Воркер отправляет задачу в планировщик, после чего он пишет результат в лог.» → Хорошо: «Воркер отправляет задачу в планировщик. После этого <уточните: воркер или планировщик> пишет результат в лог.» — «он» относится к любому из двух слов мужского рода. Исполнитель не угадан, а запрошен (RU-00).
- [README; переписывание] Плохо: «Данный флаг включает новый расчёт цены. Это обязательно для тестового контура.» → Хорошо: «Этот флаг включает новый расчёт цены. <уточните: флаг или новый расчёт> обязателен для тестового контура.» — «данный» → «этот». Голое «это» указывает на флаг или на расчёт, поэтому вопрос, не догадка (RU-00).
- [инструкция; переписывание] Плохо: «Запустите контейнер с сертификатом из Vault.» → Хорошо: «Запустите контейнер с сертификатом из Vault. <уточните: сертификат внутри образа или передаётся при запуске?>» — «с сертификатом» читается двумя способами. Текст сохранён, вопрос — одной строкой после него.
**Исключения.** Местоимение сразу после единственного подходящего существительного в том же предложении: «Скрипт создаёт файл и заполняет его». «Этот/эта/эти» + существительное. «Вы» и «мы» как участники переписки. Перед именем с идентификатором «этот» не нужен: «сервис `orders`», не «этот сервис `orders`».

### RU-22. Утвердительные формулировки
**STE:** нет аналога (RU-only), связано с 5.3 и словарём STE
**Правило.** Говорите, что сделать, а не чего не делать: «Заполните поле» вместо «Не оставляйте поле пустым», «Проверьте» вместо «Не забудьте проверить». Одно «не» на предложение, не считая грамматически обязательных «никогда не», «ничего не». Не используйте «нельзя не», «не может не», «не без», «не является не-…», «не забудьте не…». Запрет пишите как «Не + императив несовершенного вида» (см. RU-14) без второго отрицания внутри. Результат называйте положительным глаголом: «Сервис вернул ошибку», а не «Сервис не вернул успешный ответ». Опора — редполитики и практика ste-ru.
**Почему.** Логическое двойное отрицание требует вычисления в уме, и неноситель или переводчик часто вычисляет его неверно. Отрицательная команда говорит, чего избегать, но не говорит, что делать.
**Ищите.** Два и более «не» в предложении. «Нельзя не», «не может не», «не без», «невозможно не». «Не забудьте», «не оставляйте», «не пропустите». «Не» + слово с приставкой «не-/без-» («не безопасно», «не недоступен»). «Не только …, но и …».
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Не забудьте прогреть кеш перед переключением трафика.» → Хорошо: «Прогрейте кеш перед переключением трафика.» — отрицательная команда стала прямой.
- [wiki; переписывание] Плохо: «Нельзя не отметить, что ретраи не помогают при таймауте базы.» → Хорошо: «Ретраи не помогают при таймауте базы.» — «нельзя не отметить» убрано. Осталось одно «не», факт тот же.
- [спецификация; переписывание] Плохо: «Ответ без заголовка `ETag` не считается некорректным.» → Хорошо: «Ответ без заголовка `ETag` допустим.» — двойное отрицание снято. «Не считается некорректным» слабее, чем «считается корректным», поэтому «допустим», не «корректен» (RU-00).
**Исключения.** Грамматическое двойное отрицание: «никто не», «никогда не». Прямые запреты: «Не удаляйте», «Не запускайте». Термины с «не-»: «неблокирующий», «недоступен» — но не рядом со вторым «не». Статусы и сообщения системы: «Не найдено», «Не удалось подключиться».

### RU-23. Пунктуация и типографика
**STE:** 8.1, 8.2, типографика — нет аналога (RU-only)
**Правило.** Точка с запятой внутри предложения запрещена: пишите два предложения или вертикальный список. Тире « — » с пробелами ставьте между частями предложения и вместо глагола в определениях. Короткое тире «–» без пробелов — в диапазонах: «10–15 мин». Дефис «-» — внутри слов. Кавычки — «ёлочки». Прямые кавычки — только в коде. Элементы интерфейса: в plain text — «ёлочки», в Markdown — **полужирный**. Код, пути, параметры, команды — моноширинным шрифтом, не в кавычках. Буква «ё» — по RU-07. Неразрывный пробел между числом и единицей: «30 с», «10 %». Без «!» и многоточий. Опора — Розенталь, ГОСТ 8.417 (единицы) и редполитики.
**Почему.** Точка с запятой склеивает мысли в длинное предложение, и её часто ставят неверно. Дефис вместо тире и кавычки вместо моноширинного шрифта скрывают, где термин, где код, а где часть предложения.
**Ищите.** «;» вне кода и не в конце пункта списка. « - » с пробелами. Диапазон через дефис «10-15». Кавычки " " и „“ вне кода. `Код` в кавычках. Число и единица без пробела («30с»).
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Проверьте статус реплики; если лаг 5-10 с - подождите, если больше - переключите трафик.» → Хорошо: «Проверьте статус реплики. Если лаг 5–10 с, подождите. Если лаг больше 10 с, переключите трафик.» — точка с запятой → три предложения. Диапазон через короткое тире. После условия запятая, а не дефис.
- [README; переписывание] Плохо: «Задайте параметр "timeout" в файле "config.yaml" и нажмите "Сохранить"!» → Хорошо: «Задайте параметр `timeout` в файле `config.yaml`. Затем нажмите **Сохранить**.» — код моноширинным, кнопка полужирным (Markdown). «!» убран, два действия — два предложения.
- [чейнджлог; переписывание] Плохо: «Удалён флаг NEW_PRICING... релиз отменён - см выше.» → Хорошо: «Удалён флаг `NEW_PRICING`. Релиз отменён (см. выше).» — многоточие → точка, идентификатор — кодом. «См.» — только в скобках (RU-10).
**Исключения.** Код, команды, конфиги и цитаты логов — как есть, включая «;» и прямые кавычки. Точка с запятой в конце пункта списка — если такой стиль принят в проекте (одна конвенция на документ).

## D. Инструкции

### RU-24. Шаг — повелительное наклонение
**STE:** 5.3, 3.6, GR-7
**Правило.** Шаг пишите глаголом в повелительном наклонении 2-го лица множественного числа без «вы»: «Нажмите», «Запустите».
Не пишите шаг инфинитивом («Открыть терминал»), через «нужно/можно + инфинитив», «вы должны», «давайте», «мы».
Инфинитив — только в подписях кнопок, заголовках и названиях задач.
«Ты» — только по конвенции чата. В одном тексте — одна форма.
Роли называйте нейтрально: «дежурный», «автор PR». Не пишите парные формы «он(а)», «должен/должна»: имя роли снимает вопрос рода, а «должен» о требовании допустим (RU-15).
Вид глагола — по RU-14: «удалите» для разового действия, «следите» и «не удаляйте» для процесса и запрета.
**Почему.** Инфинитив и безличные формы не говорят, кто действует и обязателен ли шаг.
Читатель не отличает шаг от заголовка и от описания системы. Переводчик и агент не могут восстановить адресата.
**Ищите.** Предложение начинается с инфинитива и заканчивается точкой: «Открыть …», «Выполнить …».
«Вам необходимо», «вы должны», «вам нужно», «пользователю следует», «давайте», «теперь мы».
«Ты» и «вы» в одном тексте. Нумерованный список из инфинитивов. Парные формы «он(а)», «должен/должна» через слэш.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Перед выкаткой прогнать линтер, затем открыть PR.» → Хорошо: «1. Перед выкаткой запустите линтер. 2. Откройте PR.» — инфинитив не называет исполнителя. Два действия — два шага (RU-25).
- [README; написание] Плохо: «Теперь давайте поднимем базу: `docker compose up db`.» → Хорошо: «Запустите базу командой `docker compose up db`.» — «давайте» — туториальная форма, не команда. «Поднять» — переносное значение (RU-02).
- [wiki; переписывание] Плохо: «Дежурный должен проверить дашборд, когда он(а) заступает на смену.» → Хорошо: «В начале смены дежурный должен проверить дашборд.» — имя роли вместо «он(а)». «Должен» о требовании сохранён (RU-15).
**Исключения.** Подписи кнопок и пунктов меню — инфинитив: «Сохранить». Первая строка описания PR — по формату проекта (например, «fix notifications: remove retry»).
Заголовки процедур — «Как + инфинитив» (RU-31). Названия задач в тикетах: «Добавить индекс».
Чат на «ты», если так принято в команде. Описание обязанностей роли — не шаг, см. RU-30.

### RU-25. Одно действие — одно предложение
**STE:** 5.2
**Правило.** Одно действие — одно предложение и один нумерованный шаг.
Не склеивайте команды союзами «и», «затем», «потом», «после чего».
Порядок показывайте номерами шагов, не словами. Число шагов не ограничено.
Результат, предел или ожидаемое состояние пишите вторым предложением того же шага (см. пример 2).
**Почему.** Читатель выполняет шаги по ходу чтения: второе действие в предложении теряется, порядок приходится восстанавливать по союзам.
На «шаг 3» можно сослаться, на середину предложения — нет.
**Ищите.** Два императива в одном предложении.
«И», «затем», «потом», «после чего», «далее» между глаголами-командами. Деепричастие перед командой — см. RU-13.
Двоеточие, после которого вторая команда. «Примечание:» с пределом результата (RU-28).
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Остановите воркер, потом примените миграцию и после этого запустите воркер снова.» → Хорошо: «1. Остановите воркер. 2. Примените миграцию. 3. Запустите воркер снова.» — три последовательных действия — три шага. Порядок задаёт нумерация.
- [README; переписывание] Плохо: «Запустите `make test` и убедитесь, что все тесты прошли.» → Хорошо: «Запустите `make test`. Все тесты должны пройти.» — результат — вторым предложением того же шага, не второй командой. Проверка результата — не отдельное действие: читатель сверяет вывод команды с ожидаемым результатом.
**Исключения.** Одновременные действия — по RU-13.
Пара глаголов, которая означает одну операцию: «Сохраните и закройте файл», если интерфейс делает это одной кнопкой.
Результат действия — описательным предложением с двумя глаголами: «Сервис применит настройки и перечитает конфиг».

### RU-26. Условие, цель и время — перед командой
**STE:** 5.4, 7.2
**Правило.** Условие, цель или время ставьте перед командой и отделяйте запятой: «Если …, сделайте …», «Чтобы …, запустите …».
Условие выражайте придаточным с глаголом.
Не пишите «при + отглагольное существительное», «в случае …», «при условии, что …», «когда» в значении условия.
Одно условие на предложение. Альтернативу пишите отдельным предложением: «Иначе …».
Наречие ставьте рядом с глаголом, к которому оно относится. Проверяйте, по какую сторону запятой оно оказалось.
«Если тест падает повторно, запустите …» и «Если тест падает, повторно запустите …» — разные инструкции.
**Почему.** Читатель выполняет шаг по ходу чтения и начинает действие раньше, чем дочитает до условия.
«При + существительное» прячет субъект и время: непонятно, условие это или уже выполненный шаг.
**Ищите.** Императив в начале, а «если», «когда», «чтобы», «после того как», «только если», «кроме» — в середине или конце.
«При» + слово на «-ении», «-ании», «-ке»: «при выполнении», «при настройке».
«В случае», «при условии, что». Два «если» в одном предложении.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Откатите релиз, если доля ошибок 5xx выше 1 %.» → Хорошо: «Если доля ошибок 5xx выше 1 %, откатите релиз.» — условие впереди: читатель сначала проверит долю ошибок, потом откатит.
- [wiki; переписывание] Плохо: «При отсутствии заголовка `X-Request-Id` сервис генерирует его сам.» → Хорошо: «Если заголовка `X-Request-Id` нет, сервис генерирует заголовок сам.» — «при отсутствии» → придаточное с «если»: запятая показывает границу условия и действия. Команды здесь нет, пример показывает только замену «при + отглагольное».
- [README; написание] Плохо: «Запустите `make deps`, чтобы установить зависимости.» → Хорошо: «Чтобы установить зависимости, запустите `make deps`.» — цель впереди: читатель понимает, нужен ли ему этот шаг.
**Исключения.** Короткая отметка-событие (≤3 слов) как обстоятельство времени: «После деплоя проверьте логи», «После старта сервис читает конфиг».
«Когда» для времени, не условия: «Когда индекс построится, сервис перейдёт в статус `ready`».
Условие для целого блока шагов ставьте перед первым шагом блока.

### RU-27. Списки
**STE:** 4.3, 8.4
**Правило.** Три и более однородных элемента — вертикальный список.
Шаги нумеруйте. Наборы без порядка маркируйте.
Вводная фраза заканчивается двоеточием и сама укладывается в лимит RU-16. Контекст и оговорки — отдельным предложением перед ней.
Все пункты — в одной грамматической форме и одном падеже: шаги — императив, свойства — существительные, условия — «если …».
Пункты-предложения — с заглавной буквы и с точкой.
Пункты-фрагменты — одна конвенция на документ. По умолчанию — со строчной и без знаков. Точка с запятой в конце пункта — только если так принято в проекте.
Не больше двух уровней вложенности. В списке запретов повторяйте «Не …» в каждом пункте.
Не смешивайте шаги и описание в одном списке.
**Почему.** Перечисление из четырёх элементов внутри абзаца читатель не может ни охватить, ни пересчитать.
Пункты в разной форме ломают параллелизм: читатель не понимает, шаги перед ним или свойства.
Нумерация без порядка обещает последовательность, которой нет.
**Ищите.** Три и более однородных члена через запятую. Пункты с разных частей речи.
Разнобой знаков в конце пунктов. Вложенность глубже двух уровней.
Пункт длиннее лимита RU-16 (20 слов для шагов, 25 для описаний) или с двумя командами. Вводная фраза без двоеточия.
«Запрещается:» или «Нельзя:» + список инфинитивов.
**Плохо → Хорошо.**
- [README; переписывание] Плохо: «Сервису нужны переменные `DATABASE_URL`, `REDIS_URL`, `ORDERS_TOKEN` и `LOG_LEVEL`.» → Хорошо: «Сервису нужны переменные:» и четыре пункта маркированным списком: `DATABASE_URL`, `REDIS_URL`, `ORDERS_TOKEN`, `LOG_LEVEL` — четыре элемента в строке. Порядок не важен, поэтому маркеры, а не номера.
- [инструкция; переписывание] Плохо: «Чтобы выкатить хотфикс: - собрать образ; - прогнать тесты; - выкатываем в тестовый контур.» → Хорошо: «Чтобы выкатить хотфикс:» и шаги «1. Соберите образ.», «2. Запустите тесты.», «3. Выкатите хотфикс в тестовый контур.» — инфинитивы и «мы» сведены к императиву. Шаги пронумерованы. Объект третьего шага взят из вводной фразы, не выдуман.
- [инструкция; написание] Плохо: «Пока индекс перестраивается, нельзя: - писать в таблицу; - менять схему; - запускать бэкап.» → Хорошо: «Пока индекс перестраивается:» и пункты «Не пишите в таблицу.», «Не меняйте схему.», «Не запускайте бэкап.» — запрет повторён в каждом пункте прямой командой.
**Исключения.** Два элемента — в строке через «и». Два-три значения в скобках: «(JSON, XML, CSV)».
В чате формат проще, но пункты держите в одной форме. Как считать слова в списках — counting.md.

### RU-28. Примечание — только информация
**STE:** 5.5
**Правило.** В примечании — только факты, без которых процедура всё равно выполнима.
Ни команд («не забудьте», «обратите внимание»), ни «должно», ни «нельзя», ни пределов.
Предел или результат шага — вторым предложением того же шага (RU-25).
Информация о риске для данных, прода, денег и безопасности — в предупреждение (RU-29).
Примечание пишите по правилам описания: настоящее время, лимит 25 слов (RU-16).
Проверка: прочитайте процедуру без примечаний.
Если её нельзя выполнить правильно, перенесите недостающее в шаг.
**Почему.** Читатели пропускают примечания. Команда в примечании — скрытый шаг, его не выполнят.
Императив превращает примечание в шаг и ломает нумерацию процедуры.
**Ищите.** «Примечание:», `[!NOTE]`, `{% note info %}`, «P.S.», «кстати» рядом с императивом, «должен», «нельзя», «не забудьте», «обратите внимание», «не больше».
Риск потери данных под маркером «Примечание». Полный список — warnings.md.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Примечание: не забудьте включить фича-флаг `orders_v2` после выкатки.» → Хорошо: отдельный шаг «После выкатки включите фича-флаг `orders_v2`.» — команда в примечании — шаг, который пропустят вместе с примечанием.
- [инструкция; переписывание] Плохо: «2. Задайте `RATE_LIMITER_LIMITS`. Примечание: значение не должно превышать 1000.» → Хорошо: «2. Задайте `RATE_LIMITER_LIMITS`. Максимум — 1000.» — предел параметра — часть шага, в котором параметр задают. Предел записан утвердительно (RU-22).
- [чат; переписывание] Плохо: «Кстати, обратите внимание: индекс строится в фоне и не блокирует запись.» → Хорошо: «Индекс строится в фоне и не блокирует запись.» — «обратите внимание» — команда без действия. Сам факт и есть примечание.
**Исключения.** Нет. Разметка примечаний и полные примеры — warnings.md.

### RU-29. Предупреждение — уровень, команда, последствие
**STE:** 7.1, 7.2, 7.3
**Правило.** Структура блока: маркер уровня → [условие,] команда → последствие отдельным предложением. Уровень выбирайте по последствию.
**ПРЕДУПРЕЖДЕНИЕ** — необратимое или масштабное последствие: данные, прод, деньги, безопасность, люди.
**ВНИМАНИЕ** — восстановимое: откат, повторный запуск, потеря времени. Два риска — два блока. Если разделить нельзя, ставьте высший уровень.
Блок стоит перед шагом, к которому относится. Команда — императив (RU-24), не «не рекомендуется» и не «будьте внимательны».
Последствие — конкретное: что сломается, что потеряется, обратимо ли. Лимит — 20 слов на предложение (RU-16).
Маркеры «ОСТОРОЖНО», «Важно», «NB», «!!!» не используйте. Таблица уровней и разметка — warnings.md.
**Почему.** Без уровня читатель не отличает «остановит прод» от «полезно знать». Предупреждение после шага прочитают после выполнения.
Объяснение впереди прячет команду. «Могут быть проблемы» не даёт оценить риск.
**Ищите.** «Важно», «NB», «Осторожно», «!!!». Блок после шага. «Поскольку», «во избежание» в начале блока.
«Рекомендуется», «будьте аккуратны», «непредсказуемые последствия» внутри. Полный список — warnings.md.
**Плохо → Хорошо.**
- [инструкция; переписывание] Плохо: «Важно!!! Не запускайте `reset-queue.sh` на проде, потому что он очистит очередь уведомлений без бэкапа.» → Хорошо: «ПРЕДУПРЕЖДЕНИЕ: Не запускайте `reset-queue.sh` на проде. Скрипт очищает очередь уведомлений без бэкапа.» — потеря данных без бэкапа — высший уровень. Последствие — отдельным предложением.
- [инструкция; переписывание] Плохо: «2. Выполните `make regen`. Осторожно: команда перезапишет ваши правки в `gen/`, так что закоммитьте их заранее.» → Хорошо: «ВНИМАНИЕ: Перед `make regen` сделайте коммит правок в `gen/`. Команда перезаписывает правки в `gen/`.» и затем «2. Выполните `make regen`.» — блок перед шагом. Теряются только правки одного человека без коммита: это потеря времени, поэтому «ВНИМАНИЕ», не «ПРЕДУПРЕЖДЕНИЕ».
- [инструкция; переписывание] Плохо: «ВНИМАНИЕ: так как реплика отстаёт от мастера до 5 с, не читайте из неё сразу после записи.» → Хорошо: «ВНИМАНИЕ: Не читайте из реплики сразу после записи. Реплика отстаёт от мастера до 5 с.» — сначала команда, потом причина.
**Исключения.** В чате и тикете маркер «ВНИМАНИЕ:» в начале сообщения допустим, но не обязателен. Порядок «команда → последствие» обязателен.
Admonition-движки (`[!WARNING]`, `{% note alert %}`) — по таблице соответствия в warnings.md.

## E. Описания и оформление

### RU-30. Описание — от общего к частному, с повтором ключевых слов
**STE:** 6.1, 6.2
**Правило.** В описании подавайте информацию постепенно: сначала что это и зачем, потом как устроено, потом детали и условия.
Одно предложение — одна тема (RU-17).
Не смешивайте в одном предложении назначение, механизм, условие и следствие.
Повторяйте ключевые слова из предложения в предложение.
Не заменяйте их синонимами, «данный», «указанный» и местоимениями (RU-21).
Ключевое слово в другом падеже — то же ключевое слово.
Введённое короткое имя («далее — шлюз») используйте дальше всегда.
Связь предложений показывайте разрешёнными связками: «затем», «поэтому», «в результате», «но».
В описании нет императива: описание сообщает, инструкция командует (RU-24).
**Почему.** Предложение с четырьмя фактами читатель перечитывает дважды.
Синоним читается как другая сущность. Агент и переводчик не могут сопоставить термины.
**Ищите.** Деепричастный или причастный оборот плюс придаточное в одном предложении.
«При этом», «в том числе» внутри предложения. Местоимения, «данный», «указанный» — см. RU-21.
Синонимы для одного объекта: сервис / приложение / компонент, ручка / эндпоинт / метод. Императив в описании.
**Плохо → Хорошо.**
- [wiki; переписывание] Плохо: «Сервис `rate-limiter`, получая лимиты из конфига `RATE_LIMITER_LIMITS`, который дежурные меняют в админ-панели, отклоняет запросы сверх лимита с кодом 429.» → Хорошо: «Сервис `rate-limiter` отклоняет запросы сверх лимита с кодом 429. Лимиты сервис берёт из конфига `RATE_LIMITER_LIMITS`. Этот конфиг дежурные меняют в админ-панели.» — назначение → источник лимитов → кто их меняет. Три предложения вместо одного с оборотом и придаточным.
- [PR; переписывание] Плохо: «Добавил кеш ответов в `notifications`. Приложение хранит его в Redis. Компонент сбрасывает кеш после обновления шаблона.» → Хорошо: «Добавил кеш ответов в `notifications`. Сервис `notifications` хранит кеш в Redis. После обновления шаблона сервис сбрасывает кеш.» — «приложение» и «компонент» читаются как другие сущности. Повтор ключевого слова снимает сомнение.
- [README; переписывание] Плохо: «Сервис рассылки отчётов для корпоративных клиентов (далее — рассыльщик) получает шаблон из `notifications`. Сервис рассылки возвращает число отправленных писем.» → Хорошо: «Сервис рассылки отчётов для корпоративных клиентов (далее — рассыльщик) получает шаблон из `notifications`. Рассыльщик возвращает число отправленных писем.» — введённое короткое имя используют всегда, иначе оно бесполезно. Сокращать можно только название длиннее трёх слов (RU-06).
**Исключения.** Страдательное причастие как термин или состояние: «сохранённый конфиг», «входящий запрос» (RU-13).
Обязанности роли — настоящим временем: «Дежурный проверяет дашборд».

### RU-31. Абзац и заголовок — одна тема
**STE:** 6.4, 6.5, 6.6 (заголовки — RU-only)
**Правило.** Один абзац — одна тема.
Первое предложение называет тему. Не начинайте абзац с подводки: «стоит отметить», «как известно», «в рамках задачи», «есть несколько нюансов».
Не больше шести предложений в абзаце. Что считать предложением и абзацем — counting.md.
Связки второй темы («также», «кроме того», «ещё») — см. RU-17: начните новый абзац.
В Markdown темы — это заголовки. Описательные разделы — именная группа: «Хранение счётчиков».
Процедуры — «Как + инфинитив»: «Как перевыпустить секрет». Одна форма на каждый тип раздела.
Описательные и процедурные разделы в одном документе — норма.
Заголовок, который задал пользователь или шаблон проекта («Как это работает» в README), не меняйте.
Без точки в конце, без Title Case (Розенталь, редполитики).
Проверка: первые предложения абзацев и заголовки складываются в план текста.
**Почему.** Читатель сканирует заголовки и первые предложения и решает, читать ли дальше.
Подводка прячет тему, вторая тема ломает поиск, длинный абзац теряет структуру.
**Ищите.** «Стоит отметить», «как известно», «в рамках», «хочу обратить внимание» в начале абзаца. Больше шести предложений.
Заголовок с точкой, вопросом, Title Case или императивом.
Описательный раздел под заголовком вида «Как …» или процедура под именной группой. Стена текста под одним заголовком.
**Плохо → Хорошо.**
- [PR; переписывание] Плохо: «Стоит отметить, что в рамках задачи поправил ретраи в клиенте `notifications`: теперь 3 попытки. Также обновил README.» → Хорошо: «Поправил ретраи в клиенте `notifications`: теперь 3 попытки.» и отдельным абзацем «Обновил README.» — подводка удалена. «Также» вводило вторую тему.
- [wiki; переписывание] Плохо: заголовки «## Настройка лимитов.» и «## Как откатить релиз» в одном документе → Хорошо: «## Как настроить лимиты» и «## Как откатить релиз» — раздел «Настройка лимитов» — пошаговая процедура под именной группой, поэтому «Как + инфинитив». Точка убрана.
- [тикет; переписывание] Плохо: «Дашборд `orders` показывает рост p99 с 12:00 МСК, при этом алерт не сработал, ещё надо бы поправить порог алерта, он сейчас 2 с.» → Хорошо: «С 12:00 МСК дашборд `orders` показывает рост p99. Алерт не сработал.» и отдельным абзацем «Порог алерта сейчас 2 с. Предлагаю поправить порог.» — симптом и предложение — две темы, два абзаца. Первое предложение каждого называет тему.
**Исключения.** Абзац из одного предложения допустим.
Заголовок-инфинитив («Откатить релиз») — если так принято в проекте. Форма одна на тип раздела.
Отглагольное существительное в заголовке описания — норма, не нарушение RU-11.

### RU-32. Конкретика: числа, единицы, даты
**STE:** 4.1, 8.6 (формат — RU-only)
**Правило.** Числа — цифрами, с единицей по ГОСТ 8.417, без точки после единицы: «15 мин», «10 %», «5 ГБ».
Дата — по ISO 8601: «2026-09-02». Время — с зоной, одна форма на документ: «14:30 МСК» или «14:30+03:00».
Разряды больших чисел — через пробел: «10 000». Диапазоны и пробел перед единицей — по RU-23.
Не пишите «вчера», «на днях», «скоро», «в ближайшее время» — только дату.
«Примерно», «около», «порядка» — только с допуском или диапазоном: «около 10 мин, не больше 15».
Абстракцию заменяйте наблюдаемым фактом. Не «нагрузка влияет на время ответа», а «на 500 RPS время ответа растёт с 50 до 300 мс».
Число в начале предложения — перестройте предложение.
В режиме переписывания недостающие значения не выдумывайте: плейсхолдер «<уточните>» и вопрос автору (RU-00).
Число с единицей, дата и идентификатор считаются одним словом (RU-16, counting.md).
**Почему.** Числа прописью не находятся поиском. «03.04» читается двумя способами.
Время без зоны в распределённой команде — источник инцидентов. «Вчера» через день теряет смысл. «Влияет» не говорит, как и насколько.
**Ищите.** Числительные прописью: «пять», «десять», «тысяча». «Сек.», «мин.», «5сек», «шт».
Даты «ДД.ММ» без года, «3 апреля», «сегодня», «вчера», «завтра», «недавно», «скоро». Время без зоны: «в 10:00», «в 10 утра».
Диапазон через дефис: «5-10». «10000» без пробела. «Около», «примерно», «порядка», «более/менее» без числа. «Корректный» без критерия проверки, «оптимальный», «влияет» без значения.
**Плохо → Хорошо.**
- [тикет; переписывание] Плохо: «Вчера таймаут к `orders_db` вырос до пяти секунд.» → Хорошо: «<уточните дату> таймаут к `orders_db` вырос до 5 с.» — «вчера» без даты тикета не восстановить: плейсхолдер и вопрос. Число цифрами с единицей.
- [чат; переписывание] Плохо: «Окно обслуживания — 05.10.2026 с 22:00 до 23:30 МСК.» → Хорошо: «Окно обслуживания — 2026-10-05, 22:00–23:30 МСК.» — дата в ISO 8601, диапазон времени через короткое тире.
- [README; переписывание] Плохо: «Скрипт обрабатывает десять тысяч строк за минуту-две.» → Хорошо: «Скрипт обрабатывает 10 000 строк за 1–2 мин.» — цифры, разряды через пробел, диапазон через тире.
**Исключения.** «Один», «два» прописью в оборотах «один раз», «в два клика». В UI-строках единицы времени — словом: «за 5 секунд» (см. genres.md §7).
В коде и конфигах — формат языка: точка как десятичный разделитель.
В чате и тикете время без даты допустимо: дата есть у сообщения. «Вчера» и «скоро» недопустимы и там.
