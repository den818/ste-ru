# Лимиты и подсчёт

Файл отвечает на три вопроса: какие лимиты действуют, что считать одним словом и что считать
предложением в Markdown. Сами правила — в `rules-ru.md` (RU-16, RU-19, RU-20, RU-25, RU-26, RU-27,
RU-31, RU-00). Лимит 20 слов для инструкций и единицы подсчёта совпадают с ГОСТ Р 58049-2017,
п. 8.2.5.1 и примечанием к нему (сверено по первоисточнику 2026-09-03, разбор — в `ste-mapping.md`).
Лимит 25 слов для описаний — из STE и практики ste-ru, в ГОСТ его нет.

## Лимиты

| Что | Потолок | Ориентир средней длины |
|---|---|---|
| Шаг инструкции, предупреждение | 20 слов в предложении | 12–15 слов |
| Описание, примечание, пояснение (любой жанр) | 25 слов в предложении | 15–18 слов |
| Абзац | 6 предложений | — |

- Лимит — потолок, не цель. Текст, в котором каждое предложение по 20 слов, читается тяжело.
- Телеграфный стиль запрещён (RU-20). Не выбрасывайте глагол, подлежащее, союз «что» и существительное при числе ради счётчика.
- Символьных лимитов нет. Длинное слово — не нарушение.
- Тип определяет лимит, а не жанр. Шаг в README или в PR — 20 слов, пояснение в инструкции — 25 слов.

## Единицы подсчёта слов

Слово — последовательность букв или цифр между пробелами. Предлоги, союзы и частицы («в», «и», «не», «же») —
отдельные слова: именно они раздувают предложение. Единицы из таблицы — одно слово, сколько бы пробелов в них ни было.

| Единица | Пример | Слов |
|---|---|---|
| Дефисное слово | `веб-сервер`, `API-ключ`, `фича-флаг`, `Санкт-Петербург`, `из-за` | 1 |
| Число | `3`, `10 000`, `0,5` | 1 |
| Число с единицей | `15 мин`, `10 %`, `500 RPS`, `5 ГБ` | 1 |
| Диапазон | `10–15 мин` | 1 |
| Код в бэктиках | `` `make check` ``, `` `RATE_LIMITER_LIMITS` `` | 1 |
| Путь, URL, адрес хоста | `/etc/orders/config.yaml`, `https://wiki.example.com/orders` | 1 |
| Ключ тикета, номер PR | `PROJ-1234`, `PR 4521` | 1 |
| Версия, код ответа с текстом | `2.1.0`, `«429 Too Many Requests»` | 1 |
| Аббревиатура | `API`, `БД`, `TLS` | 1 |
| Цитата в «ёлочках» | текст ошибки, строка из лога, название документа | 1 |
| Имя собственное, название команды или продукта | `Иван Петров`, `Redis`, `«Платформа уведомлений»` | 1 |
| Элемент интерфейса | `**Сохранить**`, `«Настройки»` | 1 |
| Скобочная вставка целиком | `(PROJ-1234)`, `(см. раздел 3)`, `(по умолчанию 30 с)` | 1 |
| Термин из глоссария проекта | `очередь задач`, `дежурный по сервису` | 1 |
| Номер шага, маркер списка, метка `ПРЕДУПРЕЖДЕНИЕ:` | `1.`, `-`, `ВНИМАНИЕ:` | 0 |

Две оговорки:

- Вставка в скобках — одно слово основного предложения, но её содержимое — отдельное предложение со своим лимитом. Что можно ставить в скобки — RU-18. Длинное пояснение вынесите из скобок в отдельное предложение.
- Цепочка родительных падежей («время ответа сервера базы данных») считается по словам. Это повод перестроить группу (RU-19), а не ввести аббревиатуру ради счётчика.

## Предложение и абзац в Markdown

| Фрагмент | Для лимита слов | Для лимита абзаца |
|---|---|---|
| Вводная фраза перед списком (до двоеточия) | отдельное предложение | вместе с пунктами — одно предложение |
| Пункт списка | отдельное предложение | часть того же предложения |
| Текст в скобках | одно слово; содержимое — отдельное короткое предложение | часть предложения |
| Заголовок | не считается | не предложение и не абзац |
| Блок кода, таблица, строка лога | не считается | не предложение |
| Сообщение в чате без пустых строк | как обычно, по предложениям | один абзац |
| Строки, разделённые пустой строкой | — | разные абзацы |

Вывод: список из семи пунктов не нарушает лимит абзаца. Но пункт длиннее 25 слов нарушает лимит слов.

## Как делить длинное предложение

Делите по мыслям, не по счётчику. Условие ставьте первым (RU-26), одно действие — одно
предложение (RU-25). Три и больше однородных элемента — вертикальный список (RU-27).
Каждое новое предложение считайте заново по таблицам выше. Делить — можно, удалять — нет: факты,
числа и хеджи исходника остаются на месте (RU-00).

## Разобранные примеры

**Пример 1** [инструкция; переписывание]. Плохо (23 слова, три действия):
«Перед запуском миграции остановите воркеры очереди `orders_queue`, дождитесь, пока в дашборде счётчик активных задач станет равен нулю, и только после этого запустите `migrate.py --target orders_db`.»

Хорошо (4, 10 и 2 слова):
1. Остановите воркеры очереди `orders_queue`.
2. Дождитесь, пока счётчик активных задач в дашборде станет равен нулю.
3. Запустите `migrate.py --target orders_db`.

**Пример 2** [PR; переписывание]. Плохо (33 слова, три мысли):
«В этом PR (PROJ-1234) поднята версия клиента `rate-limiter` до 2.1.0, при этом конфиг `RATE_LIMITER_LIMITS` теперь читается из `/etc/orders/limits.yaml`, а не из переменной окружения, так как старый способ переставал работать при значениях больше 10 000 RPS.»

Хорошо (9, 11 и 12 слов):
«Этот PR обновляет версию клиента `rate-limiter` до 2.1.0 (PROJ-1234). Чтение из переменной окружения переставало работать, если значение было больше 10 000 RPS. Поэтому конфиг `RATE_LIMITER_LIMITS` теперь читается из `/etc/orders/limits.yaml`, а не из переменной окружения.»

Здесь «2.1.0», «(PROJ-1234)», путь и «10 000 RPS» — по одному слову. Исполнитель «PR» — из исходника («в этом PR»). Связка «так как» сохранена словом «поэтому» (RU-17).

**Пример 3** [wiki; написание]. Список считается двумя способами:
«Сервис `notifications` хранит три вида данных:
- Письма хранятся в базе `notifications_db`.
- Ключи идемпотентности хранятся 24 ч в Redis.
- Логи операций хранятся 30 дней в S3.»

Для лимита слов это четыре предложения: 6, 5, 6 и 6 слов. Для лимита абзаца это одно предложение.

## Подсчёт скриптом

`<skill_dir>` — каталог скилла из сообщения о загрузке скилла.

```bash
python3 <skill_dir>/scripts/ste_check.py README.md --mode auto --terms "сервис,служба" --glossary GLOSSARY.md --json
python3 <skill_dir>/scripts/ste_check.py - --mode procedural --strict <<'EOF'
Текст для проверки.
EOF
```

- `--mode procedural` — тип «инструкция», лимит 20. `--mode descriptive` — тип «описание», лимит 25. `--mode auto` — лимит по форме предложения: 20 для пунктов списка, команд и блоков с маркером «ВНИМАНИЕ:» или «ПРЕДУПРЕЖДЕНИЕ:», 25 для остального.
- `--address vy|ty|auto` — форма обращения в командах: «нажмите» (по умолчанию), «нажми» или по большинству команд в тексте. В режиме `auto` форму задаёт большинство: команд на «ты» больше — берётся «ты», поровну — «вы». Если в тексте есть обе формы, скрипт добавляет замечание RU-24 о смешении.
- `--glossary файл` — термины проекта, по одному в строке или первой колонкой таблицы. Многословный термин считается одним словом.
- `--terms "a,b,c"` — синонимы одного понятия, опцию можно повторять. `--json` — вывод в JSON: у каждого замечания поля `"ru"` и `"line"`, плюс сводки `by_rule`, `by_ru` и `exit_code`.
- Коды выхода: 0 — замечаний нет или они ниже порога. 1 — есть замечания на уровне порога. По умолчанию порог `--fail-on error` считает только ошибки: длину и точку с запятой. Флаги `--fail-on warning` и `--strict` считают любое замечание. 2 — неверный вход: файл не читается, аргументы неверны или разметка не закрыта.
- Первая строка вывода называет тип, лимит и форму обращения: «Тип: инструкция (лимит 20 слов). Обращение: вы.». Третья — число замечаний, порог и код выхода.
- Дальше — замечания, по одному на строку, с номером правила из `rules-ru.md`: «[warn] RU-15 модальность (строка 12) — подсказка», «[ERR ] RU-16 длина предложения (строка 3) — 27 слов, лимит 20».
- Скрипт считает единицы из таблицы выше. Одним словом идут код, цитата в «ёлочках»,
  **элемент интерфейса** и скобочная вставка. Так же он считает число с единицей, диапазон,
  путь, URL, ключ тикета и версию. Дефисное слово, имя из нескольких слов и термин
  из `--glossary` — тоже одно слово.
- Содержимое скобок скрипт проверяет как отдельное предложение. Замечание — «длинная скобочная вставка» (RU-18).
- YAML-шапку, блоки кода (``` и ~~~), строки таблиц и заголовки скрипт пропускает. Блок кода закрывает только маркер того же символа длиной не меньше открывающего. Маркер из трёх знаков внутри блока из четырёх — часть кода. Незакрытая шапка или незакрытый блок дают диагностику в stderr и код выхода 2. Такой текст скрипт проверяет как обычную прозу.
- Текст замечания (`issues[].text`) дословный: inline-код, цитаты и имена в нём сохранены. Маскировка нужна только для подсчёта и поиска.

Замечание линтера → правило:

| Замечание | Правило |
|---|---|
| длина предложения | RU-16 |
| точка с запятой | RU-23 |
| модальность | RU-15 |
| страдательный залог | RU-12 |
| пустой глагол, связка «является», отглагольное существительное | RU-11 |
| канцелярская связка, «данный» | RU-01 |
| ссылочное слово | RU-21 |
| цепочка родительных падежей | RU-19 |
| деепричастный оборот, причастный оборот | RU-13 |
| отрицательное сравнение | RU-32 |
| и/или | RU-10 |
| неопределённое слово | RU-09 |
| пункт не с команды | RU-24 |
| условие после команды | RU-26 |
| длина абзаца | RU-31 |
| синонимы для одного понятия | RU-03 |

Чего скрипт не умеет:

- Узнавать имя продукта или многословный термин со строчной буквы, если его нет в `--glossary`. Такое имя скрипт посчитает по словам.
- Понимать морфологию: деепричастия на «-ая», «-яя» он знает по короткому списку, условие через «при + существительное» не видит (RU-26). «Когда» он считает маркером условия или времени, как и «если».
- Проверять смысл: выдуманные факты и смену силы утверждения (RU-00).
- Узнавать предупреждение без маркера: в режиме `auto` лимит 20 получает только блок с «ВНИМАНИЕ:» или «ПРЕДУПРЕЖДЕНИЕ:».
- Различать точку с запятой внутри предложения и в конце пункта-фрагмента. Если такая конвенция принята в проекте, второе — ложная ошибка.
