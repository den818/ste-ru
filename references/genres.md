# Плейбуки жанров

Здесь только отличия жанров: тип, аудитория, жаргон, структура результата, пример. Правила этот
файл не пересказывает — за формулировкой идите в `rules-ru.md` по номеру RU-xx. Классы жаргона и
орфография — `terms-ru.md`, предупреждения — `warnings.md`, границы скилла и форматы ответа —
`SKILL.md`. Пояснения после «—» в примерах нужны для обучения, в ответ их не выводите.

Порядок для любого жанра: тип → аудитория и жаргон → глоссарий проекта (`SKILL.md`, шаг 2) →
структура → правила жанра → линтер `scripts/ste_check.py`. Явные требования проекта важнее
плейбука: формат PR, шаблон тикета.

| Жанр | Тип | Аудитория | Жаргон |
|---|---|---|---|
| Описание PR | описание | ревьюер из команды | A, B |
| Тикет | смешанный | исполнитель из команды | A, B |
| README | смешанный по разделам | любой инженер | A |
| Wiki-страница | смешанный по разделам | любой инженер | A |
| Runbook | инструкция | дежурный | A |
| Сообщение в чате | смешанный | коллега | A, B, C при однозначности |
| Сообщение об ошибке | описание + одна команда | пользователь | A, если слово есть в интерфейсе |
| Чейнджлог | описание | пользователь продукта | A |
| Спецификация | описание | инженеры и заказчик | A |

Лимит слов задаёт тип, а не жанр: 20 — команда и предупреждение, 25 — описание (см. `counting.md`).
Жанр не в таблице (постмортем, design doc, release notes) → ближайший плейбук и `rules-ru.md`.
Постмортем пишите как спецификацию: тип — описание, аудитория — инженеры, числа и время — по RU-32.

## 1. Описание PR

**Тип.** Описание. Аудитория — ревьюер, который знает проект. «Я», «мы» и прошедшее время без «я»
(«Добавил кеш») допустимы: исполнитель — автор описания.

**Структура.** Формат PR задаёт проект: шаблон в репозитории, CONTRIBUTING, правила репозитория
или каталога. Скилл его не назначает. Инварианты:
- Сохраняйте шаблон проекта, включая место ключа тикета. Одни проекты требуют `TICKET-123: …`
  в начале заголовка, другие запрещают ключ там. Conventional Commits не меняйте.
- Заголовок от пользователя не меняйте без запроса.
- Тело — ключевые изменения и логика решений, не пересказ диффа. Markdown приветствуется.

Правил нет — предложите структуру как необязательный пример. Первая строка — `<тип> <компонент>:
<сообщение>` до 72 знаков, без точки. Английское сообщение — в повелительном наклонении (`remove`,
не `removes`), русское — инфинитивом, как название задачи (исключение RU-24). Затем пустая строка и тело.

**Правила жанра.** RU-31 — подзаголовки `##`: «Что сделано», «Почему», «Контекст». RU-04 — класс C
не используйте даже в PR. RU-00 — причину изменения не выдумывайте.

**Пример** [PR; написание]:
```
fix notifications: retry mail gateway requests on 502

## Что сделано

Если почтовый шлюз ответил 502, сервис `notifications` повторяет запрос. Число попыток — 3, пауза между ними — 200 мс.

## Почему

Во время перезапуска инстансов шлюз отвечает 502. Раньше сервис возвращал клиенту ошибку отправки. Ретраи убирают эти ошибки. Задача — PROJ-1234.
```

**Переписывание.** [PR; переписывание] Плохо: «Пофиксил таймауты в notifications, вроде бы из-за шлюза, см. PROJ-1234.» →
Хорошо: «Я исправил таймауты в `notifications`. Причина, возможно, в шлюзе. Подробности — в PROJ-1234.» — хедж «вроде бы» остался как «возможно», отсылка «см.» осталась отсылкой, жаргон класса C убран (RU-00, RU-04).

## 2. Тикет

**Тип.** Смешанный: контекст — описание, задача — инструкция. Аудитория — исполнитель из команды.

**Структура.**
1. Заголовок — инфинитив как название работы: «Добавить индекс на `orders.created_at`» (исключение RU-24).
2. Контекст: что сейчас происходит и почему это проблема. Приведите числа и ссылки на дашборды.
3. Что сделать: команды по одному действию (RU-24, RU-25).
4. Критерий готовности: проверяемый факт с числом. Не «работает быстро», а «отвечает быстрее 1 с».

**Правила жанра.** RU-20, RU-21 — тикет читают через месяц без контекста чата: полные предложения
и повтор существительного вместо «он», «это», «данный». RU-09, RU-32 — критерий готовности без оценок.

**Пример** [тикет; написание], заголовок «Добавить индекс на `orders.created_at`»:
```
## Контекст

Запрос списка заказов за день читает таблицу `orders` целиком. База отвечает на этот запрос за 12 с.

## Что сделать

Добавьте индекс по колонке `created_at` в таблице `orders`. Выкатите миграцию через пайплайн `orders`.

## Критерий готовности

База отвечает на этот запрос быстрее, чем за 1 с. Индекс есть в схеме базы `orders_db`.
```

**Переписывание.** [тикет; переписывание] Плохо: «Воркер периодически падает, в логах что-то типа `OOM killed`, скорее всего утечка.» →
Хорошо: «Воркер завершается аварийно <уточните: как часто>. В логах строка вида `OOM killed` <уточните точный текст>. Скорее всего, причина — утечка.» — хедж «скорее всего» сохранён. Частота и точный текст строки не выдуманы, а запрошены (RU-00). «Падает» — класс C, в тикете заменён (RU-04).

## 3. README

**Тип.** Смешанный по разделам. «Как это работает» — описание. «Как запустить», «Как настроить» —
инструкция. Внутри раздела типы не смешивайте. Аудитория — любой инженер.

**Структура.**
1. Первый абзац: что делает сервис и для кого.
2. «Как это работает» — описание от общего к частному (RU-30). Этот заголовок задан шаблоном README, не меняйте его.
3. «Как запустить» — нумерованные шаги (RU-24, RU-25).
4. «Как настроить» — таблица параметров: имя, тип, значение по умолчанию, назначение.

**Правила жанра.** RU-03 — один термин на весь файл: не «конфиг» в одном разделе и «настройки»
в другом. RU-04 — класс B заменяйте: «запушьте» → «отправьте в ветку».

**Пример** [README; написание]:
```
## Как это работает

`rate-limiter` считает запросы по ключу `user_id` в Redis. Лимиты хранятся в конфиге `RATE_LIMITER_LIMITS`. Если лимит исчерпан, сервис отвечает 429.

## Как запустить локально

1. Запустите Redis командой `docker compose up redis`.
2. Запустите сервис командой `make run`.
3. Откройте `http://localhost:8080/ping` в браузере. Сервис отвечает `OK`.
```

## 4. Wiki-страница

**Тип.** Смешанный по разделам, как README. Аудитория — любой инженер компании. Страницу читают через год, поэтому актуальные даты и версии полезны, если их допускает шаблон проекта.

**Структура.**
Шаблон вики важнее плейбука. Если шаблона нет, предложите такую структуру:

1. Заголовок — именная группа: «Очередь ретраев в orders».
2. Первый абзац: что это и зачем. Владелец и ссылка на код полезны, но не обязательны.
3. Разделы-описания («Схема данных», «Мониторинг»), затем разделы-процедуры («Как добавить …»).
4. Строка «Обновлено: 2026-08-30» — в шапке или в конце, по конвенции wiki.

Правите только фрагмент — не добавляйте метаданные и плейсхолдеры, которых пользователь не просил.

**Правила жанра.** RU-03, RU-30 — имена как в коде: `orders_dead_letters`, а не «таблица мёртвых
писем». Введённое короткое имя не чередуйте с синонимом. RU-32 — даты по ISO 8601 и номера версий.

**Пример** [wiki; написание], первый абзац страницы «Очередь ретраев в orders»:
```
Очередь ретраев хранит запросы, которые сервис `orders` не смог отправить в сервис `notifications`. Воркер читает очередь раз в 30 с и отправляет запросы снова. После 5 неудачных попыток воркер переносит запрос в таблицу `orders_dead_letters`.

Владелец — команда `orders`. Код — в `services/orders/retry_queue/`.
```

## 5. Runbook и инструкция

**Тип.** Инструкция. Аудитория — дежурный, который выполняет процедуру под давлением времени.
Всё, что читатель должен сделать, — команда. Всё остальное — цель, предусловие, ожидаемый
результат, предупреждение или примечание. Не вставляйте объяснительные абзацы между шагами:
цель, предусловия и результат оформляйте отдельными короткими блоками.

**Структура.**
1. Заголовок — «Как + инфинитив»: «Как перевыпустить секрет базы orders_db».
2. Цель — одно предложение: что получится в конце.
3. Предусловия: доступы, роли, инструменты. Пишите их как «Нужен доступ к Vault».
4. Предупреждение — перед тем шагом, к которому оно относится. Уровень, маркер и разметка — `warnings.md`.
5. Нумерованные шаги. Одно действие — один шаг (RU-25). Результат шага — вторым предложением.
6. Ожидаемый результат: проверяемый факт, по которому дежурный поймёт, что закончил.
7. Откат: что сделать, если результата нет.

**Правила жанра.** RU-14, RU-24 — вид глагола по разовости действия: «перезапустите», не
«перезапускайте». RU-26 — условие перед командой. RU-28 — риск и предел не прячьте в примечание.

**Пример** [инструкция; написание], страница «Как перевыпустить секрет базы orders_db»:
```
Цель: заменить пароль сервиса `orders` к базе `orders_db` без простоя.

Нужен доступ к Vault и роль `db-admin`.

1. Создайте новый пароль в Vault по пути `secret/orders/db`.
2. Примените пароль в базе командой `make db-rotate`.

   ПРЕДУПРЕЖДЕНИЕ: Перед перезапуском проверьте, что команда `make db-rotate` завершилась без ошибок. Если пароль в базе не обновлён, после перезапуска сервис `orders` потеряет доступ к базе.

3. Перезапустите сервис `orders`.

Ожидаемый результат: в логах `orders` нет ошибок `auth failed`. Дашборд **Ошибки БД** показывает 0 ошибок.

Откат: если ошибки `auth failed` есть, верните старый пароль командой `make db-rotate --rollback`.
```

Блок предупреждения стоит с отступом пункта 2. Без отступа Markdown начнёт нумерацию заново, и шаг 3 станет шагом 1.

## 6. Сообщение коллеге в чате

**Тип.** Смешанный. Аудитория — коллега, который знает контекст. Жаргон классов A и B допустим,
класс C — только если слово однозначно в этом чате. «Ты» или «вы» — по конвенции чата, одна форма
на сообщение (RU-24). Прошедшее время без «я» («Добавил кеш») допустимо: исполнитель — автор сообщения.

**Структура.**
1. Ответ или результат — первым предложением. Вопрос не пересказывайте.
2. Причина или контекст — вторым предложением, если без них ответ непонятен.
3. Что сделать дальше — командой.
4. До 6 предложений: сообщение без пустых строк — один абзац (RU-31). Код и списки не считаются.
   Если ответ длиннее, разбейте его на несколько сообщений или сократите. Можно предложить
   автору вынести подробности в тикет или wiki-страницу, но не создавайте и не публикуйте
   такой артефакт без отдельного запроса.
5. Не пишите вступлений («Привет, посмотрел») и концовок («Надеюсь, помог»).
6. Предупреждения и цитаты ошибок не сокращайте. Чужие сообщения не переписывайте, правьте только текст вокруг.

**Правила жанра.** RU-00 — хедж остаётся: «возможно, из-за кеша» не превращайте в «из-за кеша».
RU-29 — маркер «ВНИМАНИЕ:» в чате допустим, но не обязателен. Порядок «команда → последствие» обязателен.

**Пример** [чат; написание], ответ на вопрос «Откатывать релиз 2.14?»:
```
Да. Релиз 2.14 ломает вход по паролю.
1. Переключи трафик на 2.13 в балансировщике.
2. Откати релиз 2.14.
Без переключения клиенты получат 500 на 1–2 мин.
```

**Переписывание.** [чат; переписывание] Плохо: «Похоже, что 500 из-за кеша, можно попробовать сбросить, но не уверен» →
Хорошо: «Возможно, ошибки 500 связаны с кешем. Можно попробовать сбросить кеш, но я не уверен.» — хедж и неуверенность сохранены, объект «кеш» назван в каждом предложении (RU-00, RU-21).

## 7. Сообщение об ошибке и UI-строка

**Тип.** Описание плюс одна команда. Аудитория — пользователь продукта, часто не инженер. Жаргон —
только слова класса A, которые пользователь видит в интерфейсе продукта. Остальное — русским
словом: «сервис уведомлений», не «бэкенд нотификаций».

**Структура сообщения об ошибке.**
1. Факт: что не получилось.
2. Причина — если она известна. Если нет, пропустите: не выдумывайте.
3. Действие: что сделать пользователю. Одна команда.

**UI-строки.** Подпись кнопки — инфинитив: **Сохранить**, **Повторить**, **Закрыть**.
Заголовок диалога — именная группа. Плейсхолдер поля — пример значения без «введите».
Без «!», без «Упс», «Что-то пошло не так», извинений и шуток.

**Правила жанра.** RU-12 — безличное «Не удалось …» здесь допустимо: исполнитель ошибки
пользователю не важен, а выдумывать его нельзя (RU-00). RU-32 — единицы времени в UI-строках
пишите словом: «за 5 секунд», не «за 5 с». RU-22, RU-23 — «Введите 6 цифр», не «Нельзя вводить буквы».

**Пример** [сообщение об ошибке; написание]:
```
Не удалось отправить письмо. Почтовый сервер не ответил за 5 секунд. Попробуйте ещё раз через минуту.
```

## 8. Чейнджлог

**Тип.** Описание. Аудитория — пользователь продукта или библиотеки. Читатель ищет своё изменение глазами, поэтому держите одну форму на весь файл.

**Структура.**
1. Заголовок версии: номер и дата по ISO 8601: `## 2.14.0 — 2026-08-30`.
2. Группы по типу: «Добавлено», «Исправлено», «Удалено» — если так принято в проекте.
3. Один пункт — одно изменение. Пункт — предложение с подлежащим-сущностью («Сервис `notifications` …», «Флаг … удалён»)
   или именная группа («Ретраи запросов …»). «Добавили …» от имени команды — только если так принято в проекте.

**Правила жанра.** RU-27 — одна грамматическая форма и одна пунктуация на весь файл. RU-17 —
«Добавили X и исправили Y» — два пункта. RU-32 — номер версии и дата, без «в ближайшем релизе».

**Пример** [чейнджлог; написание]:
```
## 2.14.0 — 2026-08-30

- Сервис `notifications` повторяет запрос к почтовому шлюзу после ответа 502.
- Сервис `notifications` больше не теряет письмо при таймауте.
- Флаг `USE_LEGACY_TEMPLATES` удалён.
```

## 9. Спецификация и ТЗ

**Тип.** Описание. Аудитория — инженеры и заказчик. Каждое предложение — проверяемое требование или определение.

**Структура.**
1. Назначение и границы: что система делает и чего не делает.
2. Термины: таблица «Термин — определение». Дальше — только эти слова.
3. Требования: нумерованные, по одному на предложение, с числами и единицами. Затем ограничения.

**Модальность.** По умолчанию — «должен» и «может» (RU-15). Шкала RFC 2119 работает, только если
документ объявил её в начале: «Слова «должен», «следует», «может» имеют значение по RFC 2119».
Без объявления «следует» запрещено. Шкалы не смешивайте.

**Правила жанра.** RU-20 — подлежащее в каждом требовании: «Сервис», «Клиент», «API». RU-19 —
именные группы до 2 родительных: «лимит запросов клиента». RU-30 — от общего к частному.

**Пример** [спецификация; написание]:
```
Если клиент превысил лимит, сервис `rate-limiter` должен отвечать 429.
Сервис может кешировать лимиты до 60 с.
Сервис не должен принимать запросы без заголовка `X-Client-Id`.
```
